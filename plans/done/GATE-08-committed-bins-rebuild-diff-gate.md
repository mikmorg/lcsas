# GATE-08: no gate proves the committed recovery/bin artifacts match current source — stale tier-1/keyshare binaries can ship on every meta disc

> **STATUS: RESOLVED** — landed in `c038291` (recovery+ci: rebuild-and-diff gate for committed bin artifacts [GATE-08]); guarded by `tests/recovery_hardening/test_bin_parity_exempt_ledger.py`.

**Priority:** P2 · **Severity:** medium · **Dimension:** tests-gates-map · **Audit status:** confirmed (high confidence) · **Ledger:** untracked
**Suggested GH issue title:** Add rebuild-and-diff gate for committed recovery/bin binaries

## Problem

What the meta disc actually bundles is the *committed* binaries in
`recovery/bin/<arch>/`, regenerated by hand (e.g. commit 9dd1b8a "regenerate
lcsas-keyshare bins"). Almost every test that exercises tier-1 builds a fresh
binary from source (`recovery/build/`, via `LCSAS_RESTORE_BIN`), so a C fix
can land, pass every source-level gate, and ship to the heir as an *unfixed*
committed binary — forever, on every meta disc burned after the source fix.
The committed artifacts already show the symptom: per-arch mtimes span May 20,
May 21, May 28, May 29 and Jun 4 for the same source tree.

The only checks that touch committed bins (qemu/wine execution tests, blind
restore) are local-only and prove "it runs", not "it embodies current source".
`repro-check` compares two fresh local builds to each other — never `bin/`
against source. Since the builds are zig-cc cross-builds with a pinned
`SOURCE_DATE_EPOCH`, they are byte-reproducible: the strongest possible gate
(clean rebuild → byte-compare against the committed file) is cheap and
deterministic, and nothing runs it.

## Evidence

Re-checked 2026-06-10 against master:

- `ls -la recovery/bin/*/` — divergent mtimes per arch: x86_64 lcsas-restore
  May 28; aarch64/armv7 May 21; aarch64-macos May 20; x86_64-macos May 29;
  windows .exe May 30; all keyshare bins Jun 4 (the 9dd1b8a regen).
- `git log 9dd1b8a` — "chore(recovery): regenerate lcsas-keyshare bins from
  `make keyshare-arches`" — regeneration is a manual chore commit.
- `recovery/Makefile:459-475` — `repro-check` builds twice fresh with
  `SOURCE_DATE_EPOCH=1735689600` and `cmp`s the two builds; `bin/` never
  enters the comparison.
- `recovery/Makefile:507-512` — coverage-c Step 3 points hardening tests at
  `build/lcsas-restore` via `LCSAS_RESTORE_BIN`, i.e. fresh builds.
- `recovery/Makefile:335` — `ZIG_CC = python3 -m ziglang cc` (toolchain comes
  from the `ziglang` pip package; its version is currently unpinned anywhere).
- Checked: `lcsas-restore` has **no** `--version` flag (`main.c:78-110` usage
  block: `--repo/--password-file/--target/--snapshot/--list-snapshots/...`),
  so the audit's "cheaper --version parity" fallback would require new product
  code — another reason to prefer rebuild-and-diff, which needs none.

## Fix design

Rebuild-and-diff in CI, with the toolchain pinned so byte-identity is
meaningful rather than flaky.

1. **Pin the toolchain.** Add `recovery/TOOLCHAIN` (one line:
   `ziglang==<exact version currently on the dev VM>`); teach
   `recovery/Makefile` to warn when `python3 -m ziglang version` mismatches.
   The gate installs exactly this version.

2. **One-time regeneration commit.** Rebuild *all* committed artifacts (6 ×
   lcsas-restore, 6 × lcsas-keyshare, iso9660 where committed) with the
   pinned zig and `SOURCE_DATE_EPOCH=1735689600` (the repro-check epoch), in
   a single commit, so the gate starts green and the mtime/toolchain skew is
   flushed once. Run the local qemu/wine execution loop on the regenerated
   bins before committing (per the established cross-build verification
   practice).

3. **Local target.** `make -C recovery bin-parity`: for each committed
   binary, clean cross-rebuild into `build/parity/<arch>/` with the pinned
   epoch, then `cmp` against `bin/<arch>/<exe>`; list every mismatch and exit
   non-zero. Also fail if `git status --porcelain recovery/bin` is non-empty
   (catches locally rebuilt-but-uncommitted drift).

4. **CI workflow.** New `.github/workflows/bin-parity.yml`:
   - triggers: `push`/`pull_request` on paths `recovery/src/**`,
     `recovery/vendored/**`, `recovery/bin/**`, `recovery/Makefile`,
     `recovery/TOOLCHAIN`; plus weekly `schedule` as a backstop;
   - steps: checkout → `pip install -r <(echo "ziglang==$(cat
     recovery/TOOLCHAIN | cut -d= -f3)")` (or simply `pip install
     "$(cat recovery/TOOLCHAIN)"`) → `make -C recovery bin-parity` (~5-8 min
     for all targets on ubuntu-latest).

5. **Edge case — a non-deterministic target.** If any target (most plausibly
   Mach-O) proves non-byte-reproducible across runner/dev environments even
   with pinned zig+epoch, do not weaken the gate globally: add the target to
   a tracked `recovery/BIN_PARITY_EXEMPT` file with an issue number, and have
   `bin-parity` print it loudly. The ledger test pattern from GATE-06 applies.

Migration/compat: none — binaries on already-burned meta discs are immutable
history; this gate only protects future builds.

## Tests & gates

- `.github/workflows/bin-parity.yml` — the gate itself; always-on for C/bin
  paths, weekly otherwise. Verify once with a scratch branch that edits a
  comment in `recovery/src/lcsas-restore/main.c` *without* regenerating bins
  → red; after `make -C recovery bin-parity`-guided regen → green.
- `make -C recovery bin-parity` — local pre-push loop for anyone touching C.
- Existing local qemu/wine tests (`test_tier1_aarch64_qemu.py`,
  `test_tier1_windows_wine.py`) — unchanged; they remain the "it runs" half
  on regen commits, GATE-03 adds the macOS half.

## Acceptance criteria

- [ ] `make -C recovery bin-parity` passes on master after the regeneration
      commit; mtime spread is irrelevant thereafter (content-compared).
- [ ] Scratch branch with a source edit and stale bins turns bin-parity red,
      naming the stale file(s).
- [ ] `recovery/TOOLCHAIN` exists and the workflow installs exactly that
      ziglang version.
- [ ] Any exemption (if needed) carries an issue number in
      `recovery/BIN_PARITY_EXEMPT` and is printed in the gate output.
