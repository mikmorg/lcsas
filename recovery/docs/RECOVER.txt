LCSAS RECOVERY TOOLCHAIN -- ON-DISC RESTORE MANUAL
=======================================================

PURPOSE

This document describes how to restore files from an LCSAS optical
archive using only the tools bundled on the meta disc.  It assumes
nothing about the computer you restore on beyond a working
POSIX-like OS with shell access.

PREREQUISITES

You will need:
  - The LCSAS meta disc (BD-R / DVD), labelled LCSAS_META.
  - The repository password (set when the archive was created).
  - A target directory with free space of AT LEAST the archive size
    (the size shown by `lcsas restore plan`, or the snapshot size) on
    BOTH the target disk and the pack-cache disk (default: your home
    folder, see "THE TOOLS FOLDER") --
    restore.sh checks this for you before any password or disc prompt
    and refuses with the exact numbers if either disk is too small.
    Override with LCSAS_SKIP_SPACE_CHECK=1 if you know better.

DECISION FLOW

  Q: Do you have a working OS?
     NO  -> Use any other computer, or boot a current live-Linux
            USB stick on this one.  See BOOT.txt for the steps.
            (The LCSAS discs themselves are NOT bootable.)
     YES -> Continue.

  Q: Can you mount the meta disc as an ISO9660 filesystem?
     NO  -> See "REPAIRING A DAMAGED DISC" below.
     YES -> mount it read-only:

         mount -o ro /dev/sr0 /mnt                 (block device)
       OR
         mount -o loop,ro path-to-iso.iso /mnt     (ISO file)

  Q: Does /mnt contain restore.sh and recovery/bin/<arch>/lcsas-restore?
     YES -> primary path:

         sh /mnt/restore.sh /tmp/restored latest

       This asks a few questions (see "WHAT restore.sh ASKS"), then
       writes restored files under /tmp/restored.  The script
       auto-detects architecture and falls back through the cascade
       if the primary binary is missing.

     NO  -> fall back to the Python reader (tier 3) from a
            data disc that ships its own standalone_restorer.py.
            You first need to assemble a pack cache from the disc
            (see "Manual pack assembly" in docs/TROUBLESHOOTING.md), then run:

         python3 /mnt/standalone_restorer.py \
             --repo /tmp/cache \
             --password-file /tmp/pwfile \
             --target /tmp/restored

IF THE COMPUTER REFUSES TO RUN THE TOOLS

The programs on the disc are fine; a safety setting on the computer
is in the way.  The fix is the same everywhere: copy the meta disc to
a folder the computer lets you run programs from, and run the copy.
It needs about 1 GB of free space; delete the copy afterwards.

  macOS -- "cannot be opened because the developer cannot be
  verified", or the restore stops with "Killed".  macOS has marked
  the files as downloaded ("quarantine"), which happens after copying
  them from a disc image or another computer:

      cp -R /Volumes/<label> ~/lcsas-meta
      xattr -dr com.apple.quarantine ~/lcsas-meta
      sh ~/lcsas-meta/restore.sh ~/restored

  Linux -- "Permission denied"; restore.sh reporting that the meta
  disc "lacks all recovery binaries" with each tier "not executable"
  although the files are there; or the restore quietly falling back
  to the slow Python reader (tier 3).  The files sit on a filesystem
  that may not run programs: a FAT/exFAT USB stick (it drops the
  executable bit) or any mount with the "noexec" option:

      cp -R /media/$USER/<label> ~/lcsas-meta
      chmod -R u+x ~/lcsas-meta/recovery/bin
      sh ~/lcsas-meta/restore.sh ~/restored

A plain optical disc rarely needs this: restore.sh already copies
itself and the binaries off a read-only disc into its tools folder
(see "THE TOOLS FOLDER") before running them.  It is for copies on USB
sticks, downloaded disc images, and locked-down computers.  (The
binaries carry no Apple or Microsoft developer signature, so a
cautious OS treats them as software from an unknown source.)

WHAT restore.sh ASKS

Run from the META disc on a terminal, restore.sh asks these questions,
in this order.  Each one says how to answer.

  1. Your NEWEST data disc.  When no data disc is in yet, it asks you
     to take the META disc out and put in the data disc with the
     latest year, and then the highest number, in its label: for
     example, LCSAS_CD700_2026_0002 is newer than LCSAS_CD700_2025_0019.
     Each disc holds every backup set's list of snapshots as it was
     when that disc was made, so the newest disc knows the newest
     snapshots, and any backup set added after the META disc was made.
     Press ENTER once the disc is in (if it does not open by itself,
     mount it: sudo mount /dev/sr0 /mnt).  restore.sh prints the
     full label it found.  The name the computer shows for a disc may
     be cut short; the full label is printed on the disc and in its
     VOLUME_INFO.txt.  S then ENTER skips this question and uses the
     copies on the META disc.  Q then ENTER stops (exit code 65).

  2. The backup set, when the discs hold more than one.  The sets are
     listed by name, with a note when a set's password is split into
     share cards:
         1) documents
         2) photos (password split: any 2 of 3 share cards)
     Type the number, the name, or the set's id (its folder name
     under metadata/).  Q then ENTER, or the end of the input, stops
     (exit code 65).

  3. The password.  What you type is not shown.  An empty answer is
     asked again, and so is a password the backup set does not
     accept: it is checked before the restore starts.  Q then ENTER
     stops (exit code 77).  A password that is just the letter q
     cannot be typed here: put it in a file and use --key FILE.
     When the set's password is split, restore.sh asks for the share
     cards instead (see "SHARE CARDS (SPLIT PASSWORDS)").

  4. The discs, one by one, while the restore runs (see "MULTI-DISC
     RESTORE").

  5. After a restore that succeeds, when the discs hold another set:
         Restore another backup set from these discs? [y/N]
     y asks for the folder to restore it into and starts again at
     question 2, with no META disc and nothing copied again.  ENTER
     takes a NEW folder beside the first (for example ~/restored-2):
     two sets restored into one folder would be mixed together.  Q
     then ENTER at the folder question restores no other set.  N or
     ENTER ends the restore, and the tools folder is deleted (see
     "THE TOOLS FOLDER").

Question 1, the check of the password, and question 5 come only on a
terminal: never when the answers come from a pipe or a script.  To
run with no questions at all, give the answers in advance (see
"ENVIRONMENT VARIABLES"):

    LCSAS_REPO=photos LCSAS_PWFILE=/path/to/password-file \
    LCSAS_NEWEST_DISC_PROMPT=0 LCSAS_ANOTHER_SET=0 \
        sh /mnt/restore.sh ~/restored

CASCADE DETAILS

The restore.sh script tries these in order.  Tiers 1-2 share NO
Python dependency; the BARE MINIMUM restore path ends after tier 2.

  Tier 1.  bin/<arch>/lcsas-restore    prebuilt static C89 binary
                                       (fastest; depends only on
                                       musl libc + kernel)

  Tier 2.  bin/<arch>/rustic-static    vendored Rust binary
                                       (fallback when tier 1 won't run;
                                       pinned upstream artifact)

  Tier 2b. bin/<arch>/restic           stock upstream restic/rustic --
           (or restic/rustic on PATH)  an independent, widely-audited
                                       reader of the SAME repository
                                       format, using ZERO LCSAS code.
                                       Tried before the Python last
                                       resort so an heir who cannot
                                       run, or does not trust, our
                                       binaries still gets an automatic
                                       restore.  Needs a data/ tree that
                                       holds a single repository
                                       (skipped on the multi-disc
                                       layout).  Full manual equivalent:
                                       RESTORE_STANDARD_TOOLS.txt.
  ─────────────────────────────────────────────────────────────────
  ^^ BARE MINIMUM PATH (zero Python).  If your future system has a
     working CPU and a kernel that can load a static binary, the
     data can be restored.
  ─────────────────────────────────────────────────────────────────

  Tier 3.  standalone_restorer.py      the Python reader, LAST RESORT
                                       (only invoked if every C/Rust
                                       option failed; skip entirely
                                       with LCSAS_ALLOW_PYTHON_TIER=0)

If every tier fails, you have a hardware/environment problem.  See
"REPAIRING A DAMAGED DISC" below.  See docs/TIERS.txt for the full
design rationale.

Before dispatching to a tier, restore.sh pre-flights each binary
with a size check plus a `--help` dry-run.
If a binary is zero-byte, wrong-arch, or otherwise unrunnable, you
will see a line like:
    [tier N] /path/to/binary is present but failed pre-flight
    (zero-byte / wrong arch / corrupted binary); skipping
This is NORMAL, not a fatal error -- restore.sh then falls through to
the next available tier.  The pre-flight exists because POSIX `sh`
will exec an empty file as a no-op script that exits 0, so without
this guard a bit-rotted tier-1 binary would silently claim success
and you would get nothing.

LIST AVAILABLE SNAPSHOTS

  /mnt/recovery/bin/<arch>/lcsas-restore \
      --repo /mnt/repo \
      --password-file /tmp/pw \
      --list-snapshots

Output:

  ID        TIME                          PATH
  a1b2c3d4  2026-01-15T10:30:00.000Z      /home/alice
  e5f6g7h8  2026-02-12T08:15:00.000Z      /home/alice

RESTORE A SPECIFIC SNAPSHOT

  sh /mnt/restore.sh /tmp/restored a1b2c3d4

The snapshot argument may be 'latest', an exact ID, or a unique prefix.
restore.sh handles the disc cascade, password prompt, and pack-cache
setup automatically.  To run the underlying binary directly without
restore.sh, see the --repo / --password-file / --target / --snapshot
flag set documented in lcsas-restore --help.

CHECKING YOUR RESTORE

Every blob is authenticated and checked against its SHA-256 hash
during restore.  If any blob fails, lcsas-restore exits non-zero with
a message identifying the bad blob.  Re-run the restore with another
disc that has the same label (LCSAS burns more than one disc with
each label).

TARGET FILESYSTEM LIMITATIONS (FAT32 / EXFAT / SMB)

If your target directory lives on a filesystem that cannot store
symbolic links (FAT32, exFAT, most SMB shares, some FUSE mounts),
lcsas-restore emits a per-affected-node warning:
    WARNING: target filesystem does not support symlinks; skipped <path>
The restore then continues with the rest of the tree.  The restored
output is intentionally LOSSY on these filesystems: symlinks are
dropped, and POSIX modes / ownership may also degrade silently.
This is by design, not a corruption indicator -- the alternative
(materialising the symlink target as a regular file containing the
link string) would silently rewrite the restored data.
To preserve symlinks and POSIX metadata, restore to an ext4 / xfs /
btrfs / APFS / NTFS target instead.

RETRY SAFETY (RE-RUNNING A FAILED RESTORE)

A failed or interrupted restore is safe to re-run from the same
target directory.  When tier 1 aborts mid-file (transient disc
read failure, ENOSPC, etc.), it leaves the partially-written file
at its ACTUAL written length -- NOT padded to the expected size.
On the next run, the idempotent-resume check sees the short file,
treats it as incomplete, and re-restores from scratch.

This means you can re-run `sh /mnt/restore.sh ...` against the same
target directory without worrying about partial files being
silently treated as complete.  Files that finished cleanly on the
first pass (size matches manifest) are skipped; files that failed
are retried.  No "delete the target directory first" dance.

The first restore into a folder drops a hidden marker
(.lcsas-restore-marker) in it, naming the backup set restored there.
Because the marker is present, every re-run of that set into that SAME
folder proceeds SILENTLY -- the resume case above is never interrupted
by a prompt.  Restoring ANOTHER backup set into that folder warns
first, like a folder of your own files (below): files of both sets
with the same names would be mixed together.

If you instead point a restore at a folder that already holds YOUR
own files (no marker -- it was not made by a prior LCSAS restore),
restore.sh / restore.bat WARN you before asking for the password and
refuse unless you type YES, because restored files with the same
names would overwrite what is there now.  Safest choice: restore into
a NEW, empty folder.  To proceed non-interactively (no terminal to
type YES on), set LCSAS_FORCE_NONEMPTY_TARGET=1.  A declined prompt
exits with code 65 and writes nothing.

STOPPING AND CARRYING ON LATER

You can stop a restore at any time:

  * At a disc prompt, type q then ENTER.  restore.sh exits with code
    75 ("stopped at your request").
  * At a question restore.sh asks, type q then ENTER: exit code 65 at
    the newest data disc or the backup set, 77 at the password or a
    share card.
  * Anywhere else, press Ctrl-C.  restore.sh exits with code 130.

Once a backup set is restored there is nothing to carry on: stopping
at "Restore another backup set?" (or at the folder question after it)
ends the run, and the tools folder is deleted.

Nothing is lost.  Files restored so far stay in the target folder,
and the tools folder (below) stays, with the discs already read in
its pack cache.  restore.sh prints the command that carries on:

    sh ~/lcsas-restore-tools/resume.sh

resume.sh needs NO META disc: it runs the copy in the tools folder,
for the same backup set and the same target folder, and asks only for
the password again (it never stores the password).  It carries on
with the copy of the set's snapshots that the stopped run used, even
if a newer data disc is in the drive by then, so the files restored
before and after the stop come from the same snapshot.  The command
is printed with quotes when the folder's name needs them; copy it as
it is.  Flags you give it
are passed on, e.g.  sh ~/lcsas-restore-tools/resume.sh --key FILE.
Files that are already complete are skipped (see RETRY SAFETY), and
discs already copied into the pack cache are not asked for again.

Running restore.sh from the META disc again works too: it finds the
tools folder, uses the copy already there instead of copying again
(only a copy that finished, of the same META disc and the same
restore.sh: one that stopped part-way, say on a scratched disc, is
made again), and carries on the same way.

THE TOOLS FOLDER

Run from the META disc, restore.sh first copies what it needs into
one folder on this computer and runs from there, so the META disc can
come out of the drive.  The folder is

    $HOME/lcsas-restore-tools        (set LCSAS_TOOLS_DIR to move it)

and it holds:

  recovery/scripts/restore.sh  this script
  recovery/bin/<arch>/         the recovery programs for THIS computer
                               only (about 130 MB, not all platforms)
  recovery/docs/               these manuals
  metadata/                    every backup set's keys, index and
                               snapshots: the META disc's copy, with
                               the sets on the newest data disc you
                               put in taken from that disc
  catalog.db                   a copy of the catalog from a data disc
  pack-cache/                  the packs copied off each data disc
  resume.sh                    carries a stopped restore on (mode 700;
                               never the password)

The copy and each disc copy print a line first, because they can take
minutes on a slow drive.  The pack cache can grow to the size of the
discs it copies, so the home folder needs that much free space; the
check before the password prompt includes it.

The folder is removed when a restore succeeds and you answer N to
"Restore another backup set?": restore.sh removes what it put there,
and the folder itself if nothing else is in it.  After any other exit
(a wrong password, q at a disc prompt, Ctrl-C) it stays, so you can
carry on; delete it yourself when you no longer need it:

    rm -rf ~/lcsas-restore-tools

The copies are made writable even though a disc is read-only, so the
folder can always be removed.  A folder left by another restore.sh, or
holding the backup sets of another archive, is emptied and used again.
A folder that holds files of your own is never used or deleted
(restore.sh then uses a temporary folder, and a stopped restore cannot
carry on).  Never restore INTO the tools folder: it is deleted at the
end, so restore.sh refuses such a target (exit code 65).

ON A LIVE USB STICK the home folder is in RAM: the tools folder, and
anything restored into the home folder, is lost when the computer is
turned off.  restore.sh says so.  Carry on before turning it off, or
point LCSAS_TOOLS_DIR and the target at two separate folders on a real
disk, e.g. a USB disk:

    LCSAS_TOOLS_DIR=/media/$USER/USBDISK/lcsas-tools \
        sh /mnt/restore.sh /media/$USER/USBDISK/restored

Mount the data discs at /mnt, never at /media: mounting a disc over
/media hides the USB disk under /media/$USER.

REPAIRING A DAMAGED DISC

If the disc returns I/O errors:

  1. Make a best-effort image of the scratched disc.  No special tool
     is required -- plain dd skips over unreadable sectors and pads
     them with zeros so the image stays the right size for ECC repair:

         dd if=/dev/sr0 of=/tmp/disc.iso conv=noerror,sync bs=2048

     If you happen to have GNU ddrescue installed it does a better job
     on a badly-scratched disc (multiple passes, logged progress):

         ddrescue /dev/sr0 /tmp/disc.iso /tmp/disc.log

     ddrescue is NOT required and is NOT bundled -- dd is enough.

  2. Repair the image with the BUNDLED in-house ECC tool.  Every disc
     is augmented with DVDisaster RS03 parity (~15% of capacity), and
     the meta disc ships its own RS03 repair tool -- lcsas-ecc -- so
     you do NOT need to install dvdisaster or anything else.  The
     easiest path is the one-shot helper, which scans the image and
     offers to repair it:

         sh /mnt/restore.sh --check-disc /tmp/disc.iso

     (Or call the tool directly:
         /mnt/recovery/bin/<arch>/lcsas-ecc verify /tmp/disc.iso
         /mnt/recovery/bin/<arch>/lcsas-ecc fix    /tmp/disc.iso
      -- where <arch> is your machine's target dir under recovery/bin/.)

     With the default 15% redundancy, roughly 13-15% of unreadable
     sectors can be repaired.  Higher configured redundancy raises
     this proportionally (augmented mode may exceed the configured
     figure, so treat 13-15% as a conservative floor).  If damage
     exceeds the parity, lcsas-ecc says so and refuses a partial
     repair rather than handing back a silently-broken image.  Treat
     ANY read error as a signal to re-burn -- do not wait.

  3. After ECC repair, mount the repaired image and continue with the
     normal cascade above.  (Tier 1 also re-checks every blob it reads
     with a Poly1305 MAC + SHA-256 hash and rejects corrupt data, so a
     repair that didn't fully take is caught, never silently restored.)

PASSWORD RECOVERY

There is no password recovery path unless the archive split its
password into shares -- see "SHARE CARDS (SPLIT PASSWORDS)" below.
The password directly seeds the scrypt KDF that derives the master
key encryption key.  If you have lost the password (and hold no
share cards), the data cannot be decrypted by anyone.

If multiple key files exist under repo/keys/, lcsas-restore tries each
in turn; you only need ONE valid password.

SHARE CARDS (SPLIT PASSWORDS)

Some archives split a repository's password into N shares, each on
its own share card (any K of them rebuild it; fewer than K reveal
nothing).  An archive may split some repositories' passwords and not
others.  PASSWORD_INFO.txt on any disc states, for each repository,
whether its password was split and the K and N in effect.

restore.sh asks for the cards itself when the backup set's marker
(metadata/<id>/LCSAS_REPO.txt on the discs) says its password is
split:

    The password for photos is split into 3 share cards;
    you need any 2 of them (Split ID 01234).
    Share card 1 of 2: type all the words on one line, then ENTER
    (or Q to quit).

Type the words of exactly K different cards, one card per line; the
words show as you type, and a word may be cut to its first 4 letters.
Each card is checked on its own as you type it: a mistyped word is
named, and that card is asked for again.  The cards are then combined
with the bundled lcsas-keyshare.  If they cannot be combined (cards
from two different splits: compare the Split ID on each card), or the
password they make is not this set's, it starts again at card 1.
P then ENTER instead of a card lets you type the password itself; Q
then ENTER stops (exit code 77).  Each card you type is kept in its
own private temporary file, deleted as soon as the cards are combined
and on any exit.

To give the cards without typing them, put each card (the printed
card's text, or a file with just its words) in its own file in one
folder, and name that folder:

    LCSAS_SHARES_DIR=/path/to/cards sh /mnt/restore.sh ~/restored

A card file with a mistake in it is named and left out, and the other
cards are combined if enough of them are left.  If lcsas-keyshare
itself does not work on this computer, restore.sh says so (the cards
are not to blame) and asks for the password instead; rebuild it as
below.

Discs made by an older LCSAS have no marker, and a set whose split was
never recorded says it is not split: restore.sh then asks for the
password.  Rebuild it first, by hand:

  1. Gather any K share cards of that repository (printed pages with
     "SHARE CARD" in the title -- older cards are titled "LCSAS KEY
     SHARE" -- or the share text files).  Each card names its
     repository.

  2. On the meta disc, run the static combiner for your machine:

         /mnt/recovery/bin/<arch>/lcsas-keyshare \
             card1.txt card2.txt > repo.key

     <arch> is your machine's target dir under recovery/bin/ -- run
     `ls /mnt/recovery/bin/` to see the exact name (the burned dirs use
     rust triples, e.g. x86_64-unknown-linux-musl for a 64-bit PC,
     aarch64-unknown-linux-musl for 64-bit ARM).  Windows ships
     lcsas-keyshare.exe -- see RECOVER_WINDOWS.txt,
     "SHARE CARDS (SPLIT PASSWORDS)".

  3. If the binary will not run on your host, use the bundled
     Python fallback at the disc root:

         python3 /mnt/keyshare_combine.py \
             card1.txt card2.txt > repo.key

  4. Continue with the normal cascade above.  Type the
     rebuilt password at the  Password:  prompt, or pass the
     saved password file:

         sh /mnt/restore.sh --key repo.key --target /tmp/restored

Format + re-implementation details: docs/SHARE_FORMAT.md on the
meta disc.

DISCS WITH THE SAME LABEL

If you have more than one disc with the same label (as is the
default), they are bit-identical.  Any one working disc is enough.
To check which disc you are using:

  cat /mnt/VOLUME_INFO.txt     # label and contents, plain text
  sha256sum /mnt/MANIFEST.sha256

SUPPORT

This is an offline, after-the-fact restore.  There is no support phone
number, no vendor.  The instructions in this file, the C source under
src/, and the documents under docs/ are everything you need.

EXIT CODES

  lcsas-restore exits:
    0 -- success
    1 -- runtime error (bad password, missing file, integrity failure)
    2 -- usage error

  restore.sh exits:
    0  -- success (whichever tier ran)
    1  -- generic failure (no repo found, unsupported OS/arch, etc.)
    2  -- usage error
    64 -- no recovery method available
    65 -- you stopped at a question restore.sh asked (the newest
          data disc, the backup set, the overwrite warning for a
          folder that is not empty, or "restore into RAM anyway?"), or
          the folder to restore into is inside the tools folder
    75 -- you typed q at a disc prompt; carry on with resume.sh
    77 -- a repository key rejected the password, or you typed q at
          the password or a share card prompt
    130 / 143 -- stopped by Ctrl-C / killed; carry on with resume.sh
  On every exit but 0 the tools folder stays (see "THE TOOLS FOLDER").
Exit 64 means every tier (1, 2, 2b, AND 3) was missing or unrunnable on
the current meta disc, before any password was prompted.
This is most likely on a corrupted meta disc (all binaries lost to
bit-rot) or a wrong-arch host (e.g. an aarch64 meta disc used on
an x86_64 machine when LCSAS_TARGET was not overridden).
The diagnostic that precedes the exit names each missing tier with
its expected path; cross-reference those paths against the meta
disc contents to confirm which is the case.

ENVIRONMENT VARIABLES

These tune restore.sh's behaviour from the calling shell.  Most
heirs do not need any of them.  Set them with `export NAME=value`
before invoking restore.sh.

  LCSAS_TIER_FALLBACK=1
      Run each tier as a subprocess and fall through to the next
      tier on a non-zero exit.  Default (unset or 0) is `exec` of
      tier 1 directly, so a tier-1 crash aborts the run.  Use this
      when you suspect a tier-1 bug and want the cascade to try
      tier 2 / tier 3 instead.  Tier 3 is always exec'd (last resort,
      nothing to fall back to).  Exception: a wrong password (tier-1
      exit 77, meaning a key file positively rejected it) STOPS the
      run -- every tier reads the same keys, so retrying with another
      tier cannot help and may leave a partial tree.  Fix the
      password and re-run.  (A missing/unreadable keys directory is
      NOT treated as a wrong password; it exits 1 and falls through
      normally.)  Typing q at a disc prompt (tier-1 exit 75) also
      stops the run: it is a pause, not a failure.

      One residual on the no-tier-1 path (#399): when the tier-1
      binary is absent or won't run (bit rot, wrong arch), the
      cascade starts directly at tier 2, which has no distinct
      wrong-password stop -- a wrong password there may leave a
      partial tree in the target.  This is fixable, not
      dangerous: fix the password, delete the target directory,
      and re-run; restores are idempotent.

  LCSAS_ALLOW_PYTHON_TIER=0
      Disable tier 3 entirely, even if python3 and
      standalone_restorer.py are present.  Use this when you want a
      hard guarantee that the restore never touches Python.  If
      tiers 1 and 2 both fail to start, restore.sh exits 64.

  LCSAS_PACK_CACHE_DIR=<path>|auto|<empty>
      Opportunistic pack cache that drops repeat disc-swap requests.
      Default (unset): `auto` -> pack-cache/ in the tools folder.
      Set to a path to pin the cache to that directory.  Set to the
      empty string to disable (disk-constrained hosts only -- see
      "REDUCING SWAP FREQUENCY WITH THE PACK CACHE" below).

  LCSAS_TOOLS_DIR=<path>
      Where the tools folder goes (default ~/lcsas-restore-tools; see
      "THE TOOLS FOLDER").

  LCSAS_INTERACTIVE=on|off|auto
      Passed to the tier-1 binary as --interactive.  auto (default)
      asks at the disc prompt only on a terminal.  It also decides
      whether restore.sh asks its own extra questions (the newest
      data disc, a password asked again, another backup set): auto
      asks them only on a terminal, on asks them even when the
      answers come from a pipe (test rigs), off never asks them.

  LCSAS_REPO=<name or id>
      The backup set to restore, by its name, its plain-letters name
      (the name_cmd= line of its LCSAS_REPO.txt, as restore.bat shows
      it) or its id; skips the list of sets.

  LCSAS_PASSWORD=<password>   LCSAS_PWFILE=<file>
      The password, or a file holding it (--key FILE is the same as
      LCSAS_PWFILE); skips the password prompt.  A wrong one is not
      asked for again: the run stops with exit code 77.

  LCSAS_SHARES_DIR=<folder>
      A folder of share card files, one card per file: the password
      is rebuilt from them, with no share card prompts (see "SHARE
      CARDS (SPLIT PASSWORDS)").

  LCSAS_NEWEST_DISC_PROMPT=0
      Do not ask for the newest data disc first: use the discs
      mounted now, else the copies on the META disc.

  LCSAS_ANOTHER_SET=0
      Do not ask "Restore another backup set?" after a restore that
      succeeds.

See `sh restore.sh --help` for the full list including LCSAS_TARGET,
LCSAS_META_DISC, LCSAS_MOUNT_DIRS, LCSAS_NO_RELOCATE, and
LCSAS_PROGRESS.

MULTI-DISC RESTORE

An LCSAS archive typically spans multiple optical discs: one META disc
that carries the recovery tools, plus several DATA discs that hold the
encrypted pack files and a copy of the catalog.  The recovery tools
handle swaps interactively — but you must know what to expect and
what to do.

WHICH DISC DO I START WITH?

Run the tools from the META disc — the one labelled LCSAS_META.  It
carries the recovery binaries (bin/<arch>/) and restore.sh.  It holds
no catalog.  If you have more than one META disc, use the newest one;
every META disc can read every data disc.  If the newest one fails,
try the META disc burned closest in date to the data discs.

For the first DATA disc, insert a disc with the NEWEST label: the
latest year in the label, then the highest number (for example,
LCSAS_BD25_2027_0014 comes before LCSAS_BD25_2026_0009).  restore.sh
asks for it right after copying (see "WHAT restore.sh ASKS").  Its
list of snapshots is the newest and its catalog the fullest, so the
restore sees every backup set and needs fewer disc swaps.  Any data
disc still works.  Go by the label, not by when a disc was burned: a
disc burned later to replace a damaged one keeps the old label and
still carries the old catalog.

  1. Insert the META disc and mount it:
         sudo mount /dev/sr0 /mnt
  2. Run:
         sh /mnt/restore.sh ~/restored/ latest
  3. restore.sh copies itself, the binaries for this computer and the
     META disc's metadata into its tools folder (see "THE TOOLS
     FOLDER") so the META disc can later be ejected.  This can take a
     few minutes on a slow drive.  You will see:
         [lcsas-restore] copying the recovery tools for this computer
                         (about 130 MB) from the disc to ...
         [lcsas-restore] copied recovery binaries to ~/lcsas-restore-tools
         [lcsas-restore] copying the backup-set metadata (about 2 MB) ...
         [lcsas-restore] you may eject the meta disc when the
                         binary prompts for a data disc.
  4. It asks you to take the META disc out and put in the data disc
     with the newest label, as described above, and then for the
     backup set and its password.
  5. When the binary has loaded the index and needs a pack that lives
     on another DATA disc, it pauses and prints a prompt (see below).

WHAT THE SWAP PROMPT LOOKS LIKE

When lcsas-restore cannot find the next required pack on the currently
mounted disc it prints (to stderr):

  +----------------------------------------------------------+
  | Pack ... is required for the next file.                  |
  | ...                                                      |
  | Single-drive restore: if your machine has only ONE       |
  | optical drive, eject the META disc first, then           |
  | insert the disc named above into the SAME drive.         |
  | Insert the right disc and press ENTER to retry.          |
  +----------------------------------------------------------+

The catalog hint lines will name the label of the DATA disc you need
(e.g. "LCSAS_BD25_2026_0003") when a catalog.db is available on a
mounted disc.  If no catalog is present the prompt shows only the pack
ID and asks you to try each DATA disc in turn.

PHYSICAL SWAP STEPS (single optical drive)

  1. Note the disc label named in the prompt.
  2. Eject the current disc:
         eject /dev/sr0
     (On macOS: drutil eject)
  3. Insert the DATA disc named in the prompt.
  4. Wait for the OS to auto-mount it (typically a few seconds).
     On Linux and macOS lcsas-restore looks again every 2 seconds
     while it waits, so once the disc is mounted it carries on by
     itself ("new disc detected -- no ENTER needed").
     If auto-mount is disabled, mount it manually:
         sudo mount /dev/sr0 /mnt
  5. If nothing happens, press ENTER at the prompt.  (On Windows,
     always press ENTER: the prompt does not look on its own there.)
  6. lcsas-restore rescans the mount directories and continues.
     It names each disc it finds by the label printed on it, e.g.
         [lcsas-restore] mounted the disc labelled LCSAS_BD25_2026_0003 at /media/...
     If the wrong disc was inserted it says
         (still not found -- check the disc label and try again)
     and keeps waiting; eject and retry with the correct disc.
  7. Repeat for each additional DATA disc as prompted.

NOTE ON THE TEST RIG vs. A REAL RESTORE

Automated tests use a setuid C wrapper called disc-loader to simulate
disc swaps without human interaction.  In a real restore you must do
the eject/insert step by hand.  A passing test therefore does NOT
guarantee that the UX is smooth for a real heir — this section exists
because the test rig hid the gap for some time (see UX_CONCERNS.txt
ID 011).

EXPECTED SWAP COUNT (FIRST-CONTACT COST)

Even with the pack cache enabled, the first contact with each DATA disc
always requires a physical swap — one swap per disc, minimum.  For an
archive spread across N data discs, expect at least N swap prompts.
With the cache active each disc is needed only once (O(N) total swaps);
later restore runs find all packs in cache and need no disc at all.
Without the cache, the same disc may be requested multiple times within
a single restore run.

REDUCING SWAP FREQUENCY WITH THE PACK CACHE

By default restore.sh keeps an opportunistic pack cache in its tools
folder (LCSAS_PACK_CACHE_DIR=auto; see "THE TOOLS FOLDER").  When
lcsas-restore first reads a pack from a DATA disc it copies the entire
data/ subtree of that disc into the cache.  Subsequent packs from the
same disc are served from the local cache, not the disc, so each DATA
disc typically needs to be inserted only ONCE regardless of how many
packs it contributes to the restore.

  * To use a specific directory:   export LCSAS_PACK_CACHE_DIR=/path
  * To disable (disk-constrained):  export LCSAS_PACK_CACHE_DIR=
  * Disk cost: roughly equal to the total size of all DATA discs that
    are touched during the restore (worst case: the full archive).

IF YOU HAVE ONLY ONE OPTICAL DRIVE

You do NOT need two Blu-ray drives.  restore.sh detects that it is
running from a read-only mount (the meta disc), copies itself plus the
binaries for this computer to its tools folder (~/lcsas-restore-tools
by default), and re-executes from there.  After this relocation, no
file handles remain on the meta disc, so when the binary prompts for a
data disc you can eject the meta disc and insert the data disc into
the same drive.

The prompt explicitly tells you when to swap:

  +----------------------------------------------------------+
  | Pack ... is required for the next file.                  |
  | ...                                                      |
  | Single-drive restore: if your machine has only ONE       |
  | optical drive, eject the META disc first, then           |
  | insert the disc named above into the SAME drive.         |
  | Insert the right disc and press ENTER to retry.          |
  +----------------------------------------------------------+

Set LCSAS_NO_RELOCATE=1 to suppress the relocation step (only
useful when running the script from a writable checkout for
development).

REBUILDING THE MASTER CATALOG FROM MIXED-AGE DISCS

Every LCSAS data disc carries a disc catalog: a full copy of the
catalog as it was when that disc was burned.  (The meta disc holds no
catalog.)  If the master catalog is lost, rebuild it from any pile of
data discs:

    lcsas catalog rebuild --output master.db /mnt/disc1 /mnt/disc2 ...

CAVEAT: disc catalogs are frozen at burn time, so a box of discs
burned over several years contains CONFLICTING views of the archive.
A disc burned before a volume was recorded as DEPRECATED or DESTROYED
still records that volume as VERIFIED.

The rebuild handles this automatically: discs are merged NEWEST-FIRST
(freshness is taken from the catalog.db file timestamp and the newest
volume record inside it), and the freshest disc catalog's view wins —
including downgrades to DEPRECATED or DESTROYED.  A volume recorded
as DESTROYED is never silently resurrected by an older disc.  Feed
order does not matter; the same pile of discs produces the same
master catalog regardless of the order you list them.

When an older disc claims a volume is MORE alive than the newest disc
catalog records, the rebuild keeps the newer status and prints a
warning naming the volume:

    volume <label>: an older disc catalog records VERIFIED but a
    newer one records DESTROYED — keeping DESTROYED. ...

If you hold a disc with the label named in such a warning, it may
still be readable despite what the catalog says — check it with:

    lcsas verify <label> --disc

A restore plan generated from the rebuilt catalog will list packs
that exist only on volumes recorded as DEPRECATED or DESTROYED
separately, so you know which data depends on discs that may no
longer exist.

CAVEAT: the NEWEST burn session's volumes look unfinished after a
rebuild.  A disc catalog is copied onto its disc at STAGING time,
before the burn happens, so a disc cannot record its own burn.  The
very latest burn session therefore appears in a rebuilt catalog as
STAGING volumes with no locations and no verify history, and the
newest discs' ISO image hashes may be absent.  This is EXPECTED, not
corruption: restore still works (the packs are on the discs).  What
is missing is the record of where each disc is kept and which discs
were verified.  To re-establish it, run:

    lcsas verify <label> --disc

for each disc of that burn session you hold; this records the disc
at its location with a fresh verify.  Older burn sessions are
unaffected — their burn records were captured on later discs and are
merged back in (volume_events, burn_sessions, and session_volumes all
survive the rebuild).

OWNER HABIT: keep the latest burn session's burn receipt files
(receipts/*.json) with your printed estate papers.  After a rebuild
they re-load where the newest discs went and their ISO image hashes
in one step:

    lcsas catalog import-receipts /path/to/receipts/*.json
