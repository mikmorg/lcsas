LCSAS RECOVERY -- PRODUCTION READINESS CHECKLIST
=================================================

PURPOSE

Verify these items before relying on an LCSAS archive in a real
disaster.  Each item cites a concrete failure mode and a HOW OFTEN
indicator.  Items are grouped into three phases: one-time setup,
ongoing maintenance, and an annual drill.

────────────────────────────────────────────────────────────────────
BEFORE RELYING ON THESE DISCS  (one-time, at archive creation)
────────────────────────────────────────────────────────────────────

[ ] BINARY AUDIT — sha256sum audit of every binary in recovery/bin/
    against recovery/MANIFEST.sha256 and recovery/UPSTREAM.sha256.
    Why: a corrupted or substituted binary passes casual inspection
    but fails silently when your OS is gone and you need it most.
    How:  sha256sum -c recovery/MANIFEST.sha256
          sha256sum -c recovery/UPSTREAM.sha256
    HOW OFTEN: once at build time, repeat when recovery/bin/ changes.

[ ] NO-OS RECOVERY DRILL — verify the live-USB recovery path on a
    spare machine.  NOTE: LCSAS discs are NOT bootable.  Write a
    current live-Linux image (e.g. Ubuntu Desktop LTS) to a USB
    stick, boot the spare machine from it, mount the meta disc,
    and confirm restore.sh is reachable:
      sh /mnt/recovery/scripts/restore.sh --help
    Why: the no-OS journey is the worst credible failure mode; an
    undrilled live-USB path is an untested recovery path.
    See recovery/docs/BOOT.txt for the full procedure.
    ERRATUM: meta discs burned before 2026-06 carry stale on-disc
    text (START_HERE.txt / BOOT.txt) telling the reader to boot the
    disc directly.  That path never worked on any build.  Re-burn
    the meta disc, or store a printed correction note ("the disc is
    NOT bootable -- use another computer or a live-Linux USB") with
    the affected discs.
    AUTOMATED: that the burned docs advertise no boot-the-disc path
    is enforced by tests/recovery_hardening/
    test_boot_path_quarantined.py (always-on).  A boot-the-disc
    drill applies only if experimental/boot/ is ever revived (see
    its README for the QEMU boot-smoke revival gate).
    HOW OFTEN: once per meta disc build.

[ ] WINDOWS DOUBLE-CLICK DRILL — on a stock Windows 10/11 VM (no admin
    elevation), mount the freshly built meta ISO, then confirm the
    advertised heir journey actually works:
      [ ] File Explorer shows START_HERE.txt + restore.bat at the root.
      [ ] Double-click restore.bat -> SmartScreen -> "Run anyway".
      [ ] The script DISCOVERS the backup set (no "could not find an
          LCSAS backup set" dead-end) and reaches the "Password:" prompt.
      [ ] With >=2 tenants on the archive, a numbered selection prompt
          appears; LCSAS_REPO=<name> skips it.
      [ ] Recovery completes; files land in Documents\restored and are
          byte-equal to the source.
    Why: Windows is the single most likely OS an heir holds, and its
    repo discovery silently dead-ended before UX-01 (it probed only
    %RECOVERY%\repo / %RECOVERY%, neither of which exists on a real
    meta-volume whose repos live under metadata\<tenant>\).  Static .bat
    grep tests cannot catch a layout-contract break; only running the
    .bat against a built disc does.
    AUTOMATED: the windows-e2e workflow (INFRA-01) builds a fixture on
    Linux and runs restore.bat unattended on a windows-latest runner,
    hash-comparing the restored tree; the wine smoke
    (recovery/tests/test_restore_bat_e2e.sh) is the local pre-flight.
    Neither substitutes for a stock-VM double-click pass before relying
    on the discs.
    HOW OFTEN: once per meta disc build, and after any restore.bat change.

[ ] ENCRYPTION KEY REDUNDANCY — confirm the repository password is
    stored in at least 2 physically separate locations.  Acceptable
    forms: a printed copy in a fireproof safe, an offsite estate
    document, a Shamir-shared key split across trusted parties, or
    a hardware key manager at a second site.
    Why: see recovery/docs/CRYPTO.txt — the password directly seeds
    the scrypt KDF; there is no password-recovery path.  A single
    copy is a single point of failure.  offsite storage is not
    optional for production archives.
    DRILL: confirm the escrowed shares (or password copy) STILL
    unlock the repo — a rotated/stale escrow opens nothing and the
    failure is undetectable until recovery.  Run:
      lcsas --config lcsas.toml key verify --repo REPO \
          --share-file CARD1 --share-file CARD2   # any K of N
      # or, to test a stored password copy directly:
      lcsas --config lcsas.toml key verify --repo REPO \
          --password-file /path/to/password-copy
    Exit code 0 and an "OK:" line mean the escrow is good.  After any
    re-key, ALL old cards are void — re-split and redistribute (see
    docs/ESTATE_PLANNING.md "ROTATION").
    HOW OFTEN: verify at archive creation; re-confirm annually.

[ ] FULL TEST-RESTORE — run a test-restore of the most recent
    snapshot to a temporary directory and verify that the file
    count matches the original backup.
    How:
      mkdir -p /tmp/test-restore
      lcsas restore exec latest /tmp/test-restore
      # or using the tier-1 binary directly:
      /mnt/recovery/scripts/restore.sh /tmp/test-restore
    Compare restored file count against the original source:
      find /tmp/test-restore -type f | wc -l
    Why: an archive that was never test-restored has never been
    verified end-to-end.  Bit rot, wrong snapshot ID, or a
    misconfigured encryption key only show up when you actually
    try to read data back.
    HOW OFTEN: once at archive creation; see monthly cadence below.

────────────────────────────────────────────────────────────────────
ONGOING MAINTENANCE  (monthly, or after each new disc set)
────────────────────────────────────────────────────────────────────

[ ] MONTHLY TEST-RESTORE — restore the most recent snapshot to a
    scratch directory and confirm zero errors.  Use a tmpfs or
    dedicated scratch partition large enough for a representative
    subset of your data.
    How:
      mkdir -p /scratch/lcsas-test-restore
      lcsas restore exec latest /scratch/lcsas-test-restore
    Check the exit code; lcsas-restore exits non-zero on any blob
    integrity failure.  Discard the output when done.
    Why: optical discs degrade.  A monthly smoke-test catches bit
    rot, bad burns, or catalog drift before you need the data.
    HOW OFTEN: monthly.

[ ] VOLUME COUNT CHECK — confirm the volume count in the catalog
    matches physical disc inventory.  Run:
      lcsas status
    Compare "volumes: N burned" against the physical discs on the
    shelf.  Investigate any gap.
    Why: discs can be lost, mislabelled, or destroyed without being
    marked DESTROYED in the catalog.  A silent gap discovered during
    an emergency restore costs time you don't have.
    HOW OFTEN: monthly, or after each new disc set is burned.

[ ] BLAST-RADIUS REVIEW — ask the pre-mortem question: "if every
    copy of ONE disc fails, which data is lost?"  Run:
      lcsas status --redundancy
    to list every under-replicated pack grouped by the disc holding
    it, then for each disc flagged as a single point of failure:
      lcsas volume impact <LABEL>
    to see the affected repos, the bytes at stake, and where the
    surviving copies live (add --snapshots with the mirror mounted
    for the snapshot-level view).  Re-burn a second copy of any disc
    whose loss you cannot accept:
      lcsas stage --for-location <location>
    Why: a disc that is the only durable holder of packs is a single
    point of failure for every memory in them; without this review
    the first time you learn a disc mattered is after it has failed.
    HOW OFTEN: monthly, alongside the volume count check above.

[ ] DISC READABILITY SCAN — insert each disc in a SATA or USB BD
    drive and re-verify it against the catalog.
    How (preferred — results are RECORDED in the catalog):
      lcsas verify --all --disc
    This walks every ACTIVE copy, prompts you to insert each disc,
    checks identity (PVD Volume ID) + full device hash against the
    SHA-256 recorded at burn time, and stamps last_verified_at on
    each passing copy.  Find overdue discs first with:
      lcsas status --stale-copies
    Fallback (no catalog / bare drive — read-only surface scan, NOT
    recorded anywhere):
      dd if=/dev/sr0 of=/dev/null bs=64k status=progress
    Or use dvdisaster's read-test mode if available:
      dvdisaster -t /dev/sr0
    Why: optical media fails gradually.  A disc that reads cleanly
    today may have marginal sectors that become fatal within a year.
    The DVDisaster RS03 ECC layer can repair roughly 13-15% of
    unreadable sectors with the default 15% redundancy (higher
    configured redundancy raises this proportionally; augmented mode
    may exceed it, so treat 13-15% as a conservative floor) -- but
    only if the disc is caught early.  Treat ANY read error as a
    signal to re-burn; do not wait.  The RS03
    repair path itself (below-threshold repair restores byte-identical;
    above-threshold damage fails loud rather than silently) is verified
    against the real dvdisaster binary by
    tests/integration/test_ecc_repair.py.  That proof runs weekly in CI
    (the ecc-weekly workflow: scheduled Mondays + on any PR touching the
    ECC wrapper) and is also available locally via the opt-in
    LCSAS_ECC_REPAIR=1 invocation.
    Recording matters: the verification history travels with the
    holographic catalog onto every later disc, so an heir can ask
    "when was each copy last confirmed good?" decades from now.
    HOW OFTEN: monthly for discs less than 2 years old; weekly for
    discs older than 5 years or stored in suboptimal conditions.

[ ] OFFSITE COPY VERIFICATION — confirm that the offsite copy of
    the archive (second set of discs, remote NAS mirror, or cloud
    backup) is current.  Log the location and date checked.
    Why: a house fire, flood, or theft destroys local copies.  The
    offsite copy is not a bonus — it is the archive.
    HOW OFTEN: after each new disc set; monthly for the offsite log.

────────────────────────────────────────────────────────────────────
EMERGENCY DRILL  (annually)
────────────────────────────────────────────────────────────────────

[ ] BLIND RESTORE DRILL — perform a full blind restore on an
    air-gapped machine that has only the meta disc and data discs.
    No network.  No prior tools installed.  Start from the BIOS.
    Steps:
      1. Boot a current live-Linux USB on a clean machine (the
         discs are NOT bootable), then mount the meta disc.
      2. Follow recovery/docs/RECOVER.txt from step 1.
      3. Restore one representative snapshot to local storage.
      4. Verify file count and spot-check a handful of files.
      5. Record the date, elapsed time, and any issues in an
         audit_log.txt file stored alongside the physical discs.
    Why: the automated test suite uses a software disc-loader shim;
    it does NOT test that a human can actually bring up a live-USB
    environment, mount the meta disc, physically swap data discs,
    and recover files.  A passing CI
    gate does not substitute for a real drill.  See also
    recovery/docs/UX_CONCERNS.txt for known UX gaps, and
    recovery/docs/PHYSICAL_DISC_VALIDATION.txt for the physical-media
    burn + blind-restore + ECC-damage-and-repair runbook (the
    hardware-only complement to the software ECC tests).
    HOW OFTEN: annually, or whenever a major recovery component
    changes (new meta disc build, new tier-1 binary, new disc set).

[ ] KEY ESCROW REVIEW — review all password escrow arrangements:
    printed copies, estate documents, split-key holders.  Confirm
    each arrangement is still accessible and the holders are still
    reachable.
    Why: escrow arrangements decay.  A key holder moves, a safe is
    re-keyed, a printed copy degrades.  Catching this during a
    planned review is far better than discovering it during a
    disaster.
    HOW OFTEN: annually.

[ ] BINARY PIN REVIEW — review recovery/UPSTREAM.sha256 and
    recovery/MANIFEST.sha256.  If upstream releases (rustic, Python)
    have shipped security fixes since the last pin update, rebuild
    the meta disc and update the pins.
    Why: recovery binaries may carry CVEs.  Because the recovery
    path runs on an air-gapped machine, automatic patching never
    fires; only an explicit review catches stale pins.
    How:  sha256sum -c recovery/MANIFEST.sha256
          sha256sum -c recovery/UPSTREAM.sha256
    HOW OFTEN: annually, or when upstream publishes a security
    advisory affecting a pinned component.

JOURNEY DRILL LOG  (one line per blind-restore variant, per meta build)
────────────────────────────────────────────────────────────────────

The blind-restore drills (make blind-restore-*) are the only end-to-end
proof that an HEIR can actually recover.  They are opt-in and cost ~$5
each, so they do NOT run in CI — which means the only record that they
ran at all is this log.  Update it on every meta-disc build: one dated
row per variant.  An empty or stale row is itself the finding.

Per project policy the blind-restore agent runs on HAIKU only (not
sonnet/opus); record the model so a future reader can trust the score.
A passing drill is a full score — every check green.  (verify.sh
currently runs 16 checks; rows recorded before the 16th check landed
show /15.)

                                             out of XFAIL.list (issue #227)

  HOW OFTEN: once per meta disc build, and after any change to
  restore.sh / restore.bat, the heir docs, or a tier binary.
