LCSAS RECOVERY -- COMMON-CASE / UX CONCERNS LOG
=================================================

This file tracks every known concern that affects an AVERAGE HEIR
restoring an archive in 2030-2050.  Each item has a STATUS, a brief
description, and a mitigation strategy.

These are distinct from the 50-year survivability concerns covered
by docs/TIERS.txt + recovery/specs/.  The toolchain is engineered to
survive software-ecosystem decay; this log tracks the *current-decade*
user-experience gaps where survivability ≠ restorability.

STATUS legend:
  OPEN       not yet addressed; on the work plan
  IN PROGRESS being worked on now
  CLOSED     resolved by a specific commit
  MITIGATED  materially reduced; a residual limitation remains
  DEFERRED   accepted as a known limitation for now
  WONTFIX    intentionally not addressed (with rationale)

ID 001 -- Heirs on Windows have no restore path
────────────────────────────────────────────────────────────────────
STATUS: MITIGATED (native Windows path shipped; a SecureBoot-signed
        live-USB remains the no-OS fallback)
RESOLVED BY: UX-01 / INFRA-01 landed the full native path —
        recovery/bin/x86_64-windows/lcsas-restore.exe (built via
        zig cc), recovery/scripts/restore.bat (CMD driver mirroring
        restore.sh, with repository-metadata layout discovery), and
        recovery/docs/RECOVER_WINDOWS.txt.  A wine smoke test plus a
        two-job Windows-journey e2e gate exercise the .bat end to end.
        Residual: no Authenticode signature yet (the unsigned-binary
        concern below), and a bare no-OS machine still rides the
        live-USB route (the optical-drive-rarity concern below).
IMPACT: HIGH.  Windows is ~70% of the laptop market.  An heir with
        only a Windows laptop cannot run any of the prebuilt
        binaries; they would need to install WSL2,
        install a Linux distro, mount the disc inside WSL, and run
        the shell driver -- a multi-hour learning curve.

MITIGATION (DONE -- UX-01 / INFRA-01):
  * Cross-build lcsas-restore.exe for x86_64-windows via zig cc.
  * Ship recovery/bin/x86_64-windows/lcsas-restore.exe on the meta
    disc.
  * Ship recovery/scripts/restore.bat as a CMD-compatible driver
    that mirrors restore.sh.
  * Document the Windows workflow in docs/RECOVER_WINDOWS.txt and
    in START_HERE.txt.
  * [DONE 2026-06-11, KEY-05] Split passwords on Windows: the
    static combiner lcsas-keyshare.exe is now documented in
    RECOVER_WINDOWS.txt ("SHARE CARDS (SPLIT PASSWORDS)") and in
    restore.bat's header + password prompt, and the meta-builder
    relocates it next to lcsas-restore.exe under the on-disc
    rust-triple bin dir.  Pinned by
    tests/recovery_hardening/test_keyshare_docs.py.

ID 002 -- /restore.sh is one file among many at disc root
────────────────────────────────────────────────────────────────────
STATUS: CLOSED (#491)
RESOLVED BY: #491 -- restore-auto.sh and restore_legacy.sh moved off
             the disc root, under recovery/scripts/.
IMPACT: MEDIUM.  Heir opens disc in file explorer, sees
        15-20 files (README, README_RESTORE, restore.sh,
        restore-auto.sh, restore_legacy.sh, restore_c89.sh,
        standalone_restorer.py, tools/, lcsas/, ...).  Picking
        the right one is non-obvious.

MITIGATION:
  * Place a single START_HERE.txt at the disc root with a 1-page
    walkthrough (already partially exists -- needs improvement).
  * Rename restore.sh to restore.command on Mac-friendly discs
    (the .command extension makes Finder treat it as runnable).
  * Reduce the number of *.sh files at disc root.  Move legacy/
    auto/c89 variants under scripts/.

ID 003 -- No GUI launcher
────────────────────────────────────────────────────────────────────
STATUS: DEFERRED  (also a NON-GOAL in WINDOWS_RECOVERY_PLAN.txt: the
        .bat console UX is the common-case answer on Windows)
IMPACT: MEDIUM.  Average heir in 2040 may have never used a
        terminal.  A double-clickable launcher (.app on macOS,
        .exe with prompt on Windows) lowers the barrier.

MITIGATION (proposed, deferred):
  * Phase 5: a thin GUI launcher that wraps the binary.  Constraint:
    must not add a heavy GUI framework dependency (no Qt/Tk/Electron).
    Likely path: a 200-LOC C app using native APIs (Win32, Cocoa
    NSAlert, GTK only if X11 is acceptable for Linux).
  * Until then: rely on terminal walkthrough in START_HERE.txt.

ID 004 -- macOS Gatekeeper / Linux execstack refuses unsigned binary
────────────────────────────────────────────────────────────────────
STATUS: MITIGATED (workaround documented in START_HERE.txt and
        RECOVER.txt "IF THE COMPUTER REFUSES TO RUN THE TOOLS", #490;
        the binaries remain without a developer signature)
IMPACT: MEDIUM.  On macOS, a quarantined copy of an unsigned
        executable (files copied from a disc image or another
        computer) triggers "cannot be opened because the developer
        cannot be verified".  On Linux, a copy on a FAT/exFAT USB
        stick loses its executable bits and a "noexec" mount refuses
        to run anything; restore.sh then skips tiers 1-2 (falling to
        the slow tier 3, or reporting that the disc "lacks all
        recovery binaries").  A plain read-only optical disc is
        mostly unaffected: restore.sh copies itself and the binaries
        into a temporary folder before running them.

MITIGATION:
  * Done (#490): both docs tell the heir to copy the meta disc to
    the home folder and run the copy, after
        xattr -dr com.apple.quarantine ~/lcsas-meta     (macOS)
        chmod -R u+x ~/lcsas-meta/recovery/bin          (Linux)
    Checked on Linux against a real meta disc copied to a
    showexec FAT image: tiers 1-2 skipped from the stick, tier 1
    restores byte-identically from the chmod'ed copy.  The macOS
    wording is for the manual Mac drill (#475) to confirm.
  * Long term: codesign the macOS binary with an Apple Developer ID;
    sign the Windows .exe with Authenticode.  Both certificates
    expire on 1-3 year cycles, so this is current-decade only
    (Authenticode is a NON-GOAL in WINDOWS_RECOVERY_PLAN.txt).

ID 005 -- Multi-disc swap prompts are unclear
────────────────────────────────────────────────────────────────────
STATUS: CLOSED
RESOLVED BY: RECOVER.txt "MULTI-DISC RESTORE" section documents the
             exact prompt text, physical swap steps, and pack-cache
             knob (LCSAS_PACK_CACHE_DIR) that reduces swap frequency.
             Static regression test added in
             tests/recovery_hardening/test_disc_swap_docs.py.
IMPACT: HIGH.  When lcsas-restore needs a pack on a different
        volume, it currently prints "pack not found: <sha>" and
        exits non-zero.  The heir has no idea which physical disc
        to insert next.

MITIGATION:
  * Implement: when a pack is missing on the mounted disc,
    consult the disc catalog (or a new plain-text disc_index.txt
    we should write at burn time) and print:
        ==> Please insert disc:  vol-042  "Family Photos 2027 (3/8)"
        ==> Catalog says it contains pack: aa11b2c3...
        ==> Press ENTER when ready (q to abort).
  * Wait for ENTER, re-scan the data/ directory, continue.
  * Add a test that simulates a missing pack and checks the
    prompt + retry loop.

ID 006 -- Password loss = no restore possible
────────────────────────────────────────────────────────────────────
STATUS: WONTFIX-CRYPTOGRAPHIC
IMPACT: HIGHEST.  No password = no key derivation = no decryption.
        This is the actual #1 failure mode in real-world archive
        inheritance: the original owner died without telling
        anyone the password.

MITIGATION (organizational, not technical):
  * START_HERE.txt should instruct archive owners to write the
    password down and store it physically separate from the discs
    (safe deposit box, with a lawyer, in an estate planning
    document, or split into Shamir shares held by several people).
  * IMPLEMENTED (KEY-09): paper-printable "Password Card" shipped as
    docs/PASSWORD_CARD.txt (static fill-in template) plus a generator
    `lcsas --config lcsas.toml key card --repo R` that renders the card
    with a transcription CHECK CODE (first 4 hex of SHA-256(password);
    the password itself is never printed). An owner/heir checks a
    hand-copied password with `lcsas key card --check FILE --code CODE`
    (MATCH/MISMATCH). The card is an off-disc artifact by design.
  * IMPLEMENTED (UX-09): whole-archive starting sheet generator
    `lcsas --config lcsas.toml estate card --output card.txt` — one page
    covering owner, repositories, disc count (from the catalog when
    reachable, else fill-in blanks), the K-of-N share scheme when split,
    and the literal first command an heir runs per OS. Complements the
    per-repository `key card` (which records one password); the estate
    card is the heir's entry point and is stored WITH the discs (no
    secret on it).
  * Optionally: support a secondary password, held by someone
    trusted, at archive creation time.  Phase 5+.
  * No technical mitigation possible from the heir's side.

ID 007 -- Optical drives are increasingly rare on modern hardware
────────────────────────────────────────────────────────────────────
STATUS: MITIGATED (live-USB route documented + gated; USB BD reader
        still required to physically read the discs)
IMPACT: MEDIUM.  By 2030 most laptops have no internal optical
        drive.  Heirs must procure a USB BD reader (~$40,
        widely available today; uncertain for 2050).

MITIGATION:
  * Document the hardware requirement explicitly in START_HERE.txt.
  * Recommend (in archive-creation guidance) that owners also keep
    a USB BD reader physically next to the disc collection.
  * The no-OS / no-drive-bay machine route is the live-USB procedure
    (BOOT.txt OPTION 2): boot a CURRENT mainstream live-Linux image,
    then run restore.sh off the META disc through a USB BD reader.
    Rationale: a current live image is vendor-signed for UEFI
    SecureBoot (default-on on consumer machines since ~2012) and
    carries current hardware drivers, so the route keeps working on
    firmware and hardware that did not exist when the discs were
    burned.  A self-maintained boot medium has neither property --
    a 2026-frozen kernel + unsigned GRUB decays against 2040
    machines, which is why the bundled boot stack was dropped
    (experimental/boot/README.md).  The procedure's load-bearing
    content is pinned by
    tests/recovery_hardening/test_live_usb_procedure_docs.py and
    end-to-end validated (Secure-Boot QEMU drill) by
    tests/e2e/test_live_usb_restore.py [BOOT-04].
  * Residual: reading the discs still requires optical hardware --
    no code-level mitigation possible for that part.

ID 008 -- "Which disc do I start with" is undocumented
────────────────────────────────────────────────────────────────────
STATUS: CLOSED
RESOLVED BY: START_HERE.txt (rendered by src/lcsas/meta/builder.py
             _render_meta_start_here: "ONE of them will be labelled
             <prefix>_META ... Start with it"), the "Insert the disc

IMPACT: MEDIUM.  In a 50-disc archive, only the meta disc contains

    on disc labels; needs to be also on the disc's filesystem
    label so it shows up in the file explorer).
  * Have START_HERE.txt unambiguously say "look for the disc labelled
    LCSAS_META first".

ID 009 -- No confirmation step before destructive write
────────────────────────────────────────────────────────────────────
STATUS: RESOLVED (non-empty-target guard) [UX-07]
IMPACT: LOW.  lcsas-restore writes restored files directly into
        --target.  If --target already has data, files are
        overwritten without prompt.

MITIGATION:
  * DONE [UX-07]: restore.sh and restore.bat now WARN before the
    password prompt and refuse (exit 65) to write into a non-empty
    target that does not look like a previous LCSAS restore.  A hidden
    marker file (.lcsas-restore-marker) identifies prior LCSAS
    targets, so the supported idempotent-resume re-run (RECOVER.txt
    RETRY SAFETY) stays SILENT.  Override with
    LCSAS_FORCE_NONEMPTY_TARGET=1 for non-interactive use.  Empty
    targets proceed silently.  Drivers: restore.sh (~line 979),
    restore.bat (target block); tests:
    tests/recovery_hardening/test_nonempty_target_guard.py and
    tests/unit/test_restore_bat_dispatcher.py.
  * DEFERRED to a tier-1 C follow-up (T1C): --verify-only flag --
    decrypt + hash-check every blob but never write to disk, print a
    summary.  A read-only dry run is a binary feature, out of scope
    for the driver-level guard above.
    Decided against (#491): restore already authenticates every
    blob, and `lcsas verify` reads a disc back.

ID 010 -- Disc-creation date and original-archive context are opaque
────────────────────────────────────────────────────────────────────
STATUS: CLOSED (#491)
RESOLVED BY: #491 -- every data disc and the meta disc carry a
             plain-text VOLUME_INFO.txt.  On a data disc it gives the
             label, the date the volume was prepared (not burned), the
             LCSAS version and the repositories; START_HERE.txt points
             to it.
IMPACT: LOW.  The heir sees a pile of discs and cannot tell
        when they were burned, by whom, with what software version,
        or for what purpose ("photos? business records? both?").

MITIGATION:
  * volume_info.json is already written by meta/builder.py but is
    JSON.  Also write a plain-text /VOLUME_INFO.txt with:
        Burned:    2027-04-15
        By:        Alice Example <alice@example.com>
        Software:  LCSAS 1.0.0-mvp1
        Contains:  /home/alice  (snapshots 2027-04-15 onward)
        Of:        47 discs in this archive
        Total:     ~3.1 TiB original data
  * Make this file the first thing referenced from START_HERE.txt.

ID 011 -- disc-loader is test-only — no disc-swap guide for heirs existed
────────────────────────────────────────────────────────────────────
STATUS: CLOSED
RESOLVED BY: RECOVER.txt "MULTI-DISC RESTORE" section (closes #106).
             Static regression test added in
             tests/recovery_hardening/test_disc_swap_docs.py.
IMPACT: HIGH.  The automated test rig uses a setuid C wrapper called
        disc-loader to simulate disc swaps without human interaction.
        Real heirs have no equivalent; they must physically eject
        and insert discs.  No heir-facing documentation of that
        process existed, so a passing test gave false confidence
        that the UX was smooth for real heirs.

MITIGATION:
  * Added a MULTI-DISC RESTORE section to RECOVER.txt that documents
    the full swap workflow: which disc to start with (LCSAS_META),
    the exact prompt text the binary prints, the physical eject/insert
    steps (eject /dev/sr0; insert; wait; press ENTER), and the
    LCSAS_PACK_CACHE_DIR knob that reduces swap frequency.
  * Added a note in that section explicitly calling out that
    disc-loader is test-only and that a passing test does not
    guarantee smooth UX for a real heir.

ID 012 -- env-var defaults were undocumented
────────────────────────────────────────────────────────────────────
STATUS: CLOSED
RESOLVED BY: recovery/docs/ENV_VARS.txt (closes #89).
             Static regression test added in
             tests/recovery_hardening/test_env_var_docs.py.
IMPACT: MEDIUM.  LCSAS_PACK_CACHE_DIR defaulted ON (auto) and
        LCSAS_TIER_FALLBACK defaulted OFF with no documented rationale.
        Nobody could predict restore behavior without reading
        restore.sh source — violating the principle that the restore
        path must be understandable without tooling.

MITIGATION:
  * Created ENV_VARS.txt with a full variable inventory and a
    documented opt-in / opt-out principle:
      "Features that only add cost or disk use are opt-in (default OFF).
       Features that change observable behavior are also opt-in unless
       the feature is always safe and the penalty of forgetting it is
       data loss or silent failure, in which case it is opt-out
       (default ON)."
  * Every variable now has an explicit "Why this default" entry.
  * Static test pins the file's existence and the presence of the
    rationale so renames or stripping of the defaults column are caught
    before merge.
