LCSAS RECOVERY -- TIER STRUCTURE
=================================

WHY TIERS?

The recovery cascade is layered so that if any single component fails
(binary won't run, language interpreter is missing, etc.), the next
tier still gets you to the same outcome: plaintext files on disk.

Tiers 1-2 are the BARE MINIMUM PATH.  They share zero dependencies
beyond a kernel and a static libc baked into the binary.  If your
future system has those two things and one working CPU, the data can
be restored.

Tier 3 is the OPTIONAL OVERFLOW.  It only runs if every C-based
option failed AND the heir has not opted out via
LCSAS_ALLOW_PYTHON_TIER=0.

THE TIERS

  ┌────┬──────────────────────────────┬─────────────────────────────┐
  │ #  │ Implementation               │ Runtime dependencies        │
  ├────┼──────────────────────────────┼─────────────────────────────┤
  │ 1  │ C reader (prebuilt)          │ kernel + libc (static)      │
  │    │ bin/<arch>/lcsas-restore     │ (musl baked in)             │
  ├────┼──────────────────────────────┼─────────────────────────────┤
  │ 2  │ rustic (vendored static)     │ kernel + libc (static)      │
  │    │ bin/<arch>/rustic-static     │                             │
  ╞════╪══════════════════════════════╪═════════════════════════════╡
  │ B  │   BARE MINIMUM PATH ENDS HERE                              │
  ╞════╪══════════════════════════════╪═════════════════════════════╡
  │ 3  │ Python reader                │ python3 (>=3.10)            │
  │    │ python_reader.py       │ stdlib only (no pip needed) │
  └────┴──────────────────────────────┴─────────────────────────────┘

DESIGN INVARIANT

The bare-minimum path (tiers 1-2) is proven Python-free by
``recovery/tests/test_bare_path.sh``:

  1. Statically inspect ``scripts/restore.sh`` -- the slice from
     "Tier 1:" to "BARE-MINIMUM PATH ENDS HERE" must contain no
     ``python`` or ``.py`` reference (in executable code; comments
     are skipped).

  2. Build a synthetic restic repository.  Strip every python
     interpreter from PATH by prepending a shim directory that exits
     127 for anything named ``python*``.  Set
     ``LCSAS_ALLOW_PYTHON_TIER=0``.  Invoke ``scripts/restore.sh``.
     Check that the restore succeeds.

  Run as: ``make -C recovery test-bare-path``

OPTING OUT OF TIER 3

If you want a hard guarantee that the restore never touches Python:

  LCSAS_ALLOW_PYTHON_TIER=0 sh /restore.sh --restore-folder /tmp/restored /mnt/recovery

restore.sh will refuse to try tier 3 even if python3 and
python_reader.py are both present.

TIER-2 ON MULTI-DISC ARCHIVES

Tier 2 (rustic-static) skips itself entirely on multi-disc archives
because rustic cannot drive the LCSAS disc-swap protocol -- it
expects every pack to live under a single ``$REPO/data/`` tree.
When restore.sh detects the multi-disc layout (the repository
metadata on the meta disc has no ``data/`` subdir), it prints a
one-line skip diagnostic and falls through directly to tier 3.

On a multi-disc archive the effective cascade is therefore
TIER 1 -> TIER 3; tier 2 is a single-disc-only fallback.
An heir with a multi-disc archive should treat tier 1 as the
primary AND the only practical pre-Python fallback.

ON WINDOWS (restore.bat)

restore.bat runs tier 1 (lcsas-restore.exe) and, when tier 1 is
present, tier 2 (rustic-static.exe) only for a backup set whose
folder holds its own data\.  It has no tier 2b and no tier 3: the
Python reader is a manual step (RESTORE_WINDOWS.txt, "MANUAL PYTHON
RESTORE").  It has no LCSAS_TIER_FALLBACK knob:
  * tier 1 exits 0: done.
  * tier 1 exits 77 (wrong password) or 75 (q at the disc prompt):
    stop, keep the tools folder, never tier 2.
  * any other exit, for a set read from the discs (no data\ in its
    folder): stop, keep the tools folder and say how to carry on.
    Tier 2 could only fail there (#615).
  * any other exit, for a set with its own data\: try tier 2.
  * no lcsas-restore.exe at all (antivirus quarantined it, say), for
    a set read from the discs: stop at once, before the folder and
    the password, with exit 64 and a message that the program is
    missing and may have been removed by antivirus (#631).  Tier 2
    cannot ask for discs, so it never runs.  Restore the .exe
    (RESTORE_WINDOWS.txt, "SMARTSCREEN WARNING") and start again from
    the META disc, or use the Python reader.  For a set with its own
    data\: try tier 2.

TIER 2b: STOCK RESTIC / RUSTIC (INDEPENDENT AUDITED READER)

After tier 2, restore.sh automatically tries a stock restic (the
cryptographically-audited Go original) -- the per-target copy bundled
at bin/<arch>/restic, or any restic/rustic on the heir's PATH --
before falling through to the Python tier.  restic is a fully
independent implementation that restores the same repository
byte-identically (proven by test_stock_restic_compat.py), so an heir
who cannot run, or does not trust, the binaries we shipped still gets
an automatic restore using only widely-audited third-party tools.
Like tier 2 it needs a single-disc $REPO/data/ tree; the fully MANUAL
standard-tools procedure (multi-disc reassembly included) is
recovery/docs/RESTORE_STANDARD_TOOLS.txt.

The tier-1-missing fallback journey on a multi-disc archive (tier 1
absent -> tier 2 skipped -> tier 3 completes) is pinned
deterministically by
tests/recovery_hardening/test_restore_sh_tier1_missing_multidisc.py
AND has passed live blind restores: promoted out of the XFAIL ledger
(tests/e2e/cdemu_blind_restore/XFAIL.list) on 2026-06-15 after scoring
a full 16/16 on two consecutive blind runs (issue #227).

TIER BINARY PRE-FLIGHT

Before dispatching, restore.sh pre-flights each tier binary with
a size check plus a ``--help`` dry-run (see ``bin_preflight_ok`` in
``scripts/restore.sh``).  A zero-byte file or a wrong-arch binary
fails pre-flight and is skipped with the diagnostic:
    [tier N] ... is present but failed pre-flight ... skipping
The cascade then advances to the next available tier.  This guard
exists because POSIX ``sh`` execs an empty file as a no-op script
that exits 0 -- without the pre-flight, a bit-rotted tier-1 binary
would silently claim success and the heir would get nothing.

See ``RESTORE.txt`` (CASCADE DETAILS, pre-flight paragraph) for the
heir-facing version of this note.

DISC-INTEGRITY LAYER (BENEATH THE TIERS)

The cascade chooses WHICH TOOL reads the bytes; it assumes the bytes
themselves are intact.  That assumption is upheld by two independent
guards applied before/within any tier:

  * RS03 ECC parity (~15% of capacity), wrapped around every burned
    image, repairs bit-rotted / scratched sectors back to their
    original bytes.  The parity is spent at restore time by the
    BUNDLED in-house repair tool ``lcsas-ecc`` -- a small C89 RS03
    decoder cross-built for all six approved targets and shipped on the
    meta disc next to ``lcsas-restore`` -- so the repair half of this
    layer needs NOTHING installed (no dvdisaster, no ddrescue).  The
    heir-facing entry point is ``restore.sh --check-disc <image>``
    (``restore.bat --check-disc`` on Windows): it runs
    ``lcsas-ecc verify`` and, on damage, offers ``lcsas-ecc fix``.
    An image with no ECC data (``lcsas-ecc``'s exit 2) ends the check
    with the script's exit 5: 2 is the scripts' usage error (#887).
    The parity format is dvdisaster's RS03, unchanged, so the newest
    meta disc's ``lcsas-ecc`` repairs every disc already burned.
  * The tier-1 binary then authenticates every blob (Poly1305 MAC +
    SHA-256 content hash) and REFUSES corrupt data rather than
    propagating it -- so disc corruption is either repaired by ECC or
    rejected loudly, never silently restored.

The RS03 repair path is validated two ways.  An always-on, no-dvdisaster
self-repair gate (``tests/e2e/test_ecc_selfrepair_no_dvdisaster.py``)
corrupts an augmented image and repairs it with ONLY the bundled
``lcsas-ecc``, asserting byte-identical extraction.  A cross-conformance
gate against the real dvdisaster binary
(``tests/integration/test_ecc_repair.py``, opt-in:
``LCSAS_ECC_REPAIR=1 pytest ... -m integration``) proves the in-house
decoder reads dvdisaster-written parity:

  * test_rs03_repairs_bitrot_byte_identical -- augment an image with
    RS03 ECC, overwrite data sectors (simulated bit-rot), repair, and
    confirm every file extracts byte-for-byte identical.
  * test_rs03_fails_loud_when_damage_exceeds_capacity -- damage beyond
    the ECC correction capacity makes repair REPORT FAILURE (no silent
    partial restore), so the restore aborts instead of trusting an
    un-repairable disc.

The physical-media half (a real burned disc read by a real optical
drive, with physically induced damage) is hardware-gated and specified
in ``recovery/docs/PHYSICAL_DISC_VALIDATION.txt``.

CONFIDENTIALITY (what a STOLEN disc gives an adversary): the integrity
guards above keep the bytes intact and authentic; they do NOT keep them
SECRET.  Every data disc carries its full disc catalog in plaintext
(since v1.0.0-rc9 without snapshot source folders, tags and
descriptions, which stay inside the encrypted snapshot files, #733),
and every disc carries every repository's password-locked key files, so
the password is the only thing protecting your data against unlimited
offline guessing.  The stolen-disc threat model, the entropy guidance,
and the no-rotation reality are documented in
``docs/DISC_CONFIDENTIALITY.md`` (bundled on every meta disc).

TIER 3: WHICH PYTHON

restore.sh tries, in this order, and takes the first one that
actually STARTS and is Python 3.10 or newer, the oldest Python the
reader runs on (#804):

  1. the CPython bundled for this computer, bin/<arch>/python/, on
     its own;
  2. the same CPython run through the musl loader the disc carries
     next to it (Linux x86_64 and aarch64 only):

         bin/<arch>/python/lib/ld-musl-<arch>.so.1 bin/<arch>/python/bin/python3

  3. python3, then python, on PATH.

Step 2 exists because the bundled Linux builds are linked against
musl and need its loader (/lib/ld-musl-<arch>.so.1), which stock
Debian, Ubuntu and Fedora do not have.  There the bundled python3
fails with "not found" on its own.  musl's loader runs the program
named after it, so the disc's copy runs the bundled Python with no
root and nothing installed (#714).  restore.sh says in one line which
one it used and why.  If none runs, tier 3 says so, with the reason for
the bundled one: not executable here (no run permission, or a folder
mounted noexec), a loader or library it needs is missing (the musl
loader, on the musl builds), a program for another kind of computer,
older than Python 3.10, or a processor too old for it (an illegal
instruction).  A python3 on PATH that is older than 3.10 is named too.

ARMV6 (RASPBERRY PI 1 AND ZERO)

The 32-bit ARM programs on the disc (bin/armv7-*: lcsas-restore,
rustic-static, lcsas-shares, lcsas-ecc and the bundled Python) are
built for ARMv7.  On an ARMv6 processor (uname -m says armv6l: a
Raspberry Pi 1 or Zero, not a Zero 2) each one stops at once with an
illegal instruction (checked under qemu-arm -cpu arm1176, #803).
restore.sh says so and does not run them.  What still works there:
a python3 of 3.10 or newer installed on the computer (tier 3; slow on
such a small computer), and the stock restic (tier 2b, built for ARMv6
too) for a backup set that is in one folder on a disk.  Or restore on
a newer computer (a Raspberry Pi 2 or newer is ARMv7 or later).

The loader comes from a fixed Alpine Linux release (musl 1.2.6),
pinned by SHA-256 in recovery/UPSTREAM.sha256 like the other
upstream programs.  The 32-bit ARM CPython is a glibc build and needs
no loader; the macOS and Windows builds need none either.

TIER 3: SPEED

Tier 3 needs nothing but Python, but it uses a native AES when one is
safe here and gives the right answer.  It picks, once per run, the
first of these that passes a known-answer test (NIST SP 800-38A) and a
cross-check against the built-in code:

  1. the OpenSSL library, loaded into Python (ctypes).  Windows: the
     libcrypto DLL that comes with the bundled Python.  Linux: only
     when the Python is a glibc build (a host python3), never the
     bundled musl Python, which may run through the bundled loader on
     a glibc host and must not load the host's library.  Never macOS.
     A library is tried in a separate Python process first, so a
     crash there cannot stop the restore.
  2. the openssl command (OpenSSL or LibreSSL), if it is on PATH.
     Linux and macOS hosts usually have it.  NOTE: openssl takes the
     key only on its command line.  That key is the repository's data
     key, not your password, but with it and the discs anyone can read
     every file in that repository.  While openssl runs, other users
     of the same computer can read it (ps, /proc).  A computer that
     logs the commands it runs (process accounting, an audit log)
     also writes it to that log, where it stays.  So restore on a
     computer only you use and that keeps no such log, or skip the
     openssl command with LCSAS_TIER3_AES=pure:
       LCSAS_TIER3_AES=pure sh restore.sh ...
     The pure-Python AES is slow (about 2 hours per GB).
  3. the built-in pure-Python AES (slow, always there).

The reader prints one line saying which it uses, for example
"AES-256-CTR: using the openssl command (/usr/bin/openssl, ...)".
LCSAS_TIER3_AES=auto (default), ctypes, openssl or pure overrides the
choice.  If a native AES fails during the restore, the reader goes
on with the built-in one.

Measured on the lab VM (2026-11-13, one x86_64 core, the bundled
Python with the openssl command):

  photos, video, archives (data that does not compress)
                                about 8.6 MB/s, about 2 minutes per GB
  text and documents (compresses about 3x)
                                about 0.85 MB/s, about 20 minutes per GB
  a 200 MB mix of both          112 seconds

The pure-Python zstd decoder (about 1.2 MB/s of text) and Poly1305
(about 14 MB/s) now set the pace.  With the built-in AES instead, add
about 1.8 hours per GB stored (0.15 MB/s): the same 200 MB mix would
take about 17 minutes (worked out from a 5 MB run, not timed in
full).  Tiers 1 and 2 run at disc speed.  Tier 3 exists so that the
files that matter most can still be restored when tiers 1 and 2
cannot run; for a whole large archive, get tier 1 or 2 working
(another computer, another architecture) instead.

TIER 3: SKIP-AND-CONTINUE ON A BAD BLOB

Tier 3 (the Python reader, python_reader.py, last resort) is
TOLERANT by default: a single corrupt blob, a missing index entry, or
a disc that stays unreadable after the disc-swap retries are exhausted
records ONE failure and the restore CONTINUES, instead of aborting the
whole run on the first bad byte.  All-or-nothing is the wrong default
on the last-resort tier -- one bad blob must not cost the heir 99.9%
of an otherwise-intact family archive.

Since rc11 (#909) tier 1 does the same: a file whose pack is not
found (with no disc prompt), damaged (cut short, a MAC that fails, a
bad zstd frame, a wrong hash) or unreadable, or whose blob the index
does not hold, and a folder whose listing cannot be read, is listed
and the walk goes on, with exit 4.  Both tiers write the same reason
in RESTORE_FAILURES.txt: "pack not found: <pack id>", "pack damaged:
<pack id>", "pack unreadable: <pack id>" or "blob not in index: <blob
id>".  Tier 1 also writes each file to ``.lcsas-partial`` first (as
below).  q at the disc prompt (75) and a full disk (74) still stop
either tier.

  * Files are written to a sibling ``.lcsas-partial`` file and only
    renamed onto the final path after the last blob -- so a truncated
    file is NEVER left at a final restore path, and re-running is
    idempotent.
  * Re-running carries on (rc10, #729): a file already in the target
    with the size and modification time it has in the snapshot (within
    2 seconds, as FAT keeps times in 2-second steps) is kept and its
    data is not read again, as tier 1 and rustic do.  A file a stopped
    run left only as ``.lcsas-partial``, or one with another size or
    time, is restored again.  ``--no-resume`` restores every file.
  * With LCSAS_PACK_CACHE_DIR set (restore.sh sets it), each data disc
    is copied into the pack cache when first found, so each disc is
    asked for about once (rc10, #602; see ENV_VARS.txt).
  * Like tier 1, tier 3 finds a data disc mounted one folder below a
    mount folder (/media/<user>/<LABEL>, /run/media/<user>/<LABEL>,
    /Volumes/<LABEL>), and while the meta disc is mounted it reads
    nothing from it (rc10).
  * After traversal, ``RESTORE_FAILURES.txt`` is written under the
    target listing each item not restored (path, reason, blob id), and
    plain-English summary lines are printed (see "ITEMS NOT RESTORED"
    below).
  * Exit code 4 means "finished, but K item(s) could not be restored"
    (distinct from exit 1, a setup-level failure like a missing
    repository).  Before rc10 tier 3 used exit 2 for this, which is
    also its usage error (#875).  The generated script prints a plain-English
    message, never a raw Python traceback, for any outcome.

NOTE for ALREADY-BURNED data discs: python_reader.py is
generated from the LCSAS source, so newer meta discs carry this
behaviour automatically, but data discs burned BEFORE this change ship
the older abort-on-first-error script forever.  The remedy is to run
tier 3 from the NEWEST meta disc against those old data discs -- the
packs come from the data discs, the script comes from the meta disc.
An heir always starts from the newest meta disc: every generation of
meta disc reads every disc.

LINKS, SPECIAL FILES AND ITEMS NOT RESTORED (TIERS 1 AND 3)

Tiers 1 and 3 follow the same rules, with the same wording.

Links.  Every symbolic link is restored with the target stored in the
backup, as rustic (tier 2) does: a relative link, one that points up
and out of the restore folder, an absolute one, and one that points at
nothing.  A target that is not valid UTF-8 is restored byte for byte
(rustic keeps those bytes in "linktarget_raw").  Making a link writes
nothing outside the restore folder.  The danger is a later write
THROUGH a link, so neither tier ever writes through one:

  * Restoring into a folder that already holds an earlier restore: a
    link (or a pipe, socket or device) where the backup has a file or a
    folder is removed, and the real file or folder is made in its
    place.  Files are opened so that a link is never followed.
  * A folder is never removed.  A folder where the backup has a file, a
    link or a special file is left as it is, and that item is reported
    as not restored ("a folder with this name is already there").
  * Windows: a link or junction in the way is reported, not removed.

Special files.  A FIFO (named pipe), a socket or a device is made as
rustic makes it.  A FIFO and a socket need no special rights on Linux;
a device needs root.  When the system will not make one (a device
without root; Windows has none of them), it is listed and the restore
still counts as complete: a special file holds no data.  Run the
restore as root to get devices back.

Links on a file system without links (FAT32, exFAT, most network
shares; tier 1 on Windows) are listed the same way: not restored, but
the restore still counts as complete.  Restore to ext4, xfs, btrfs or
APFS to keep them.

Every other item that is not restored is an error: a name that cannot
be decoded or that this system cannot hold, a link target that cannot
be used (empty, holding a NUL byte, longer than 4095 bytes, or badly
stored), an item type the reader does not know, a folder in the way,
or (tier 3) a file whose data could not be read.  Tier 1 then ends with
"finished with errors" and exit code 4 (rc10, #872); tier 3 also with
exit code 4 (rc10, #875; before rc10 it was 2).

Both tiers name each item in a line "NOT RESTORED: <path> (<reason>)",
write the list to RESTORE_FAILURES.txt in the restore folder (one row
per item: path, reason and blob id, separated by tabs), and end with
these lines (only those that apply):

  N special file(s) were not restored: pipes, sockets or devices that
  this system cannot create.  They hold no data.
  N link(s) were not restored: the target file system does not support
  symlinks.
  ERROR: N item(s) were NOT restored.
  See <restore folder>/RESTORE_FAILURES.txt for the list.

A run with nothing to list removes a RESTORE_FAILURES.txt that an
earlier run left in the restore folder.

As root, both tiers set each item's owner before its mode (a change of
owner clears the setuid and setgid bits) and its times last, as rustic
does.

NOTE for ALREADY-BURNED data discs: the tier-3 script on a data disc
is the one that disc was burned with; an older one skipped absolute
links and links pointing out of the restore folder.  Restore from the
newest meta disc to get these rules.

WHICH DISCS THE PROMPT NAMES (TIERS 1 AND 3)

When a pack is on no disc in the drive, the disc prompt looks the pack
up in the disc catalog and names, under "It is on any disc labelled:",
the discs of the volumes that hold it.  Both tiers use one rule (#896,
owner decision 2026-11-19):

  * Every volume holding the pack is named unless its status is
    DESTROYED.  A DEPRECATED volume IS named: one deprecated after a
    consolidation may still be on the shelf.  A lost volume (recorded
    as DEPRECATED, ADR 0003) is named too, and so is a volume with no
    disc recorded: the prompt does not read the disc records.
  * Newest volume first (the highest volume number: volumes are
    numbered in the order they were made), since the heir starts from
    the newest disc.  At most 8 discs: the 8 newest.
  * The pack is in the catalog but every volume holding it is
    DESTROYED (or none holds it): "(catalog has the pack, but lists no
    disc for it)".  Tier 3 then also names the newest disc in the
    catalog that is not DESTROYED and says the pack is on a newer one;
    it never names a DESTROYED disc there.
  * The pack is not in the catalog at all: "(catalog has no record of
    this pack ID)", and how to pick an older snapshot.

Tier 1 reads one catalog (lcsas_catalog_volumes_for_pack in
recovery/src/lcsas-restore/catalog.c).  Tier 3 reads every catalog it
has seen in the run (#635) and names the volumes any of them lists by
the same rule; a volume that any of them records as DESTROYED is not
named, since a destroyed volume never comes back.

NOTE for ALREADY-BURNED discs: before rc11, tier 1 listed the discs
oldest volume first; tier 3 also named DESTROYED volumes and listed the
discs in label order.  Use the tools on the newest meta disc.

TIER 3: ZSTD DECOMPRESSION (rustic v2 default)

rustic v2 repositories are zstd-compressed by default, so tier 3 MUST
be able to decompress zstd to be useful.  Two backends, fast-path first:

  * Native ``zstandard`` C extension, when present.  ~100x faster, but
    arch- and CPython-minor-specific: the meta builder bundles only the
    BUILD HOST's copy (tools/lib/pythonX.Y/zstandard), so it helps only
    a restore host that matches that arch + CPython minor.
  * Pure-Python decoder (lcsas.restore._zstd_pure), the fallback.  It is
    stdlib-only and ships in the LCSAS source on every meta disc AND
    inlined into the per-disc python_reader.py, so it works under
    ANY of the bundled per-target CPython interpreters (all six approved
    targets) and on any future CPython -- slower, but always available.
    The reader prints one line when it uses the slow decoder.

The build records native-zstd capability per meta disc in
volume_info.json ("zstd_support"); ``lcsas meta build`` fails loud if
the build host has no native zstandard (pass --allow-no-zstd to accept
the pure-Python-only fast-path gap).

NOTE for ALREADY-BURNED meta discs: a meta disc burned before this
change carries native-zstd-only tier-3 (host-arch only).  The remedy is
the same as above -- burn a NEW meta disc; its inlined pure-Python
decoder reads the same (already-burned) zstd-compressed data discs on
any architecture.

TIER FALLBACK ON RUNTIME FAILURES

The default cascade runs the first available tier as a subprocess (not
``exec``, so restore.sh's EXIT trap can still shred the temporary
password file -- issue #363) and exits with that tier's own status,
except a tier's 2 (its usage error), which restore.sh and restore.bat
report as 1: their own 2 means the script was called wrongly (#887).
A tier-1 crash mid-restore therefore aborts the run with no automatic
fall-through.  This matches the bare-minimum restore story: tier 1 IS
the restore, and it has to work.

To make restore.sh walk the cascade on a tier-1 runtime failure
(non-zero exit), set ``LCSAS_TIER_FALLBACK=1``.  Tiers 1 and 2 then
fall through to the next tier on a non-zero exit code.  Tier 3 is
always run as a subprocess too (its stderr is captured and replayed
on failure -- issue #240); it is the last resort, so there is nothing
to fall back to.  See ``RESTORE.txt`` ENVIRONMENT VARIABLES.

EXCEPTION -- wrong password is TERMINAL (issue #384): when tier 1
runs and exits 77, restore.sh and restore.bat STOP with a clear
message even under LCSAS_TIER_FALLBACK=1.  Every tier reads the same
keys with the same password, so a later tier could only fail the same
way -- and some (rustic) write a partial tree before rejecting the
password.

Tier 1 exits 77 when a key file CONCLUSIVELY rejected the password
with a Poly1305 MAC mismatch and none decrypted.  A softer failure --
where no key file even reached its MAC check -- keeps exit 1 and MAY
still fall through, because the password was never actually tested:
  * a missing/unreadable keys directory, or no key files at all;
  * a malformed/truncated key file (fails the ciphertext length or
    JSON checks before any MAC is computed).
A conclusive reject stays terminal even if keys/ also holds a stray or
corrupt file -- otherwise a wrong password plus one bit-rotted key
would fall through and let tier 2 leave a partial tree, the exact harm
this guards against.  The case this trades away -- a hand-rolled
restic MULTI-KEY repository where the key matching the password is the
one tier-1 cannot parse -- is not produced by LCSAS (one key file per
repository) and is a documented limitation on issue #399.

Tiers 2, 2b and 3 (rc10, #805): when one of them restores instead, a
wrong password ends the run with exit 77 too.  Tier 3 exits 77 itself
(a key file rejected the password, before anything is written).
rustic (exit 1, "No suitable key found") and restic (exit 12, "wrong
password or no key found") say it in their own words, so after a
failure restore.sh asks them again by listing the snapshots.  On a
terminal the password is asked for again, as for tier 1: restore.sh
checks it with tier 2 or 2b (listing the snapshots) before the
restore, and asks again when tier 3 exits 77.  restore.bat stops with
77 when rustic-static says so.  A tier that writes files before it
checks the password could still leave a partial tree (issue #399).

EXIT 4 -- FINISHED, NOT EVERY ITEM RESTORED (rc10, #799): when tier 1
(#872) or tier 3 (#875) exits 4, the restore FINISHED: every other item
is restored.  The items not restored are in RESTORE_FAILURES.txt
(restore.sh and restore.bat remove one an earlier run left before a
tier starts).  Tier 3 on a disc made before rc10 says the same with
exit 2, which is also its usage error; restore.sh takes that exit 2
as "finished" only when tier 3 also said so in its own words and this
run wrote RESTORE_FAILURES.txt.  restore.sh and restore.bat say "The restore finished, but N item(s) could not be
restored", name the file, and exit 4.  That is the end of that backup
set, as for a restore that succeeded: no resume.sh advice (a resume
would skip the same items again), the tools folder goes, "Restore
another backup set?" is asked, and the next tier is not tried, even
with LCSAS_TIER_FALLBACK=1 (it would restore the whole set again).
Tier 1's exit 1 (a walk that stopped early) stays a failure, with the resume
advice, even when RESTORE_FAILURES.txt is there: tier 1 has its own
code for "finished", so neither script has to guess from the file.
One exception (#887): when a row says "pack not found" (a disc that
was not in a drive, with no disc prompt; #909), running the same
restore again with that disc in restores those items.  Then both
scripts still exit 4, but keep the tools folder and resume.sh (or
"Resume LCSAS restore.bat"), say to insert the disc and run the same
restore again into the same folder, and do not offer another set.

EXIT 74 -- THE DISK IS FULL: tiers 1 and 3 exit 74 when the disk they
restore to fills up.  restore.sh and restore.bat say so, keep the
tools folder, give the resume advice and exit 74, with or without
LCSAS_TIER_FALLBACK: another tier would only fill the disk again.
restore_auto.sh stops its loop on 74.

EXIT 75 -- STOPPED AT THE DISC PROMPT (rc6): tier 1 exits 75 when the
reader types q at its disc-swap prompt (or the prompt's input ends).
Nothing is wrong: the reader paused.  The files restored so far stay,
and running the same command again carries on (finished files are
skipped).  A driver script should keep its tools folder and say how
to resume, and must NOT try the next tier: tier 2 cannot swap discs.
restore.sh and restore.bat both do so, with or without
LCSAS_TIER_FALLBACK, and exit 75 themselves.  Tier 3 uses the same
code for the same stop (rc8); restore.sh treats it the same way:
no "FAILED" report, the tools folder stays, and it exits 75.
restore.bat runs no tier 3, so it has no such case.

WHY PYTHON IS NOT ON THE BARE PATH

Python is a healthy ecosystem today, but at a 50-year horizon:

  * The CPython interpreter has fully replaced its parser, garbage
    collector, ABI, and standard library multiple times in 30 years.
    Source written today may not parse under a hypothetical Python
    of 2076.
  * Python's stdlib provides scrypt and HMAC -- but the Python reader
    also requires dataclasses, ``from __future__ import annotations``
    semantics, and pathlib edge cases that pin the minimum at
    Python 3.10 (the generated script exits with a clear message on
    anything older).  That single ecosystem version pin is itself a
    risk.
  * The interpreter binary on the meta disc depends on a C library
    and its loader (on Linux, musl's, shipped next to it) + dozens of
    optional shared libraries (ssl, expat, libffi, etc.).
    Static-link is possible but uncommon.

Statically-linked C binaries have neither of those properties.  The
prebuilt artefacts in tiers 1-2 link against musl baked into the
binary; the crypto primitives are spec-compliant per FIPS and IETF
documents that have not changed since they were published.

So: Python stays bundled as a redundant overflow path, BUT no part
of the workflow that we expect to actually run in 2076 requires it.

WHY TIER 1 IS THE PRIMARY (AND HOW WE COUNT DEPENDENCIES)

The cascade's design intent is that tier 1 -- our own lcsas-restore
binary built from C89 source against vendored sqlite + zstd -- is
the PRIMARY recovery tool.  Tier 2 (upstream rustic-static) exists
as a hedge in case our binary won't run for some reason on a
particular host; tier 3 (the Python reader) is an emergency overflow.

"Vendored" matters here.  We distinguish two senses of "third
party":

  * VENDORED SOURCE -- we ship the C source for sqlite + zstd inside
    recovery/vendored/, compile it ourselves alongside our own code,
    and pin it by SHA-256 in VENDORED.sha256 (MANIFEST.sha256 on the
    meta disc lists it too, with every other file there).  The build is reproducible from those sources.  An
    auditor can read every line that ends up in the lcsas-restore
    binary.  Vendored source is acceptable on the bare path.

  * RUNTIME DEPENDENCY -- a binary or interpreter we did not build,
    supplied by a third party (rustic; CPython) and distributed as
    an opaque prebuilt artefact.  Pinned upstream by SHA-256 in
    UPSTREAM.sha256, but the source it was compiled from is whatever
    upstream's CI did.  Runtime dependencies are explicit fallbacks
    (tiers 2 and 3); the bare path stays clean of them.

The intent: an heir with nothing but a working CPU, a kernel,
a libc, and the lcsas-restore binary off the meta disc should be
able to restore.  No `pip install`, no package manager, no upstream
release matrix that still needs to exist in 2076.  That's why
tier 1 deserves the cross-compile work even though Phase 21 shipped
the tier-2 cross-bundle as a shortcut -- see
docs/history/CROSS_PLATFORM_META_RFC.md §6 Q6.

WHY THE REBUILD-FROM-SOURCE TIERS WERE REMOVED

Earlier revisions of this cascade included two extra tiers between
the prebuilt binaries and the Python fallback:

  * Rebuild lcsas-restore from C source with whatever compiler is on
    PATH (cc/gcc/clang/tcc/pcc) plus POSIX make.
  * Rebuild rustic from vendored Rust source via cargo.

Both required an heir who has a working toolchain (C or Rust)
but does NOT have the prebuilt static binaries shipped on the same
disc AND refuses to fall back to Python.  That intersection is
effectively empty: anyone with a C compiler can run a static
binary, and anyone with Python can run the Python reader.
Removing the rebuild tiers shrinks the cascade from 5 layers to 3
without sacrificing any reachable restore scenario.

DEPENDENCY CHAIN AT A GLANCE

  Tier 1: musl libc -> CPU
  Tier 2: musl libc -> CPU
  Tier 3: python3 -> libc -> CPU

  The deepest bare-minimum chain is tier 1 or tier 2: 2 dependencies,
  each individually replaceable.

INVOCATION

  # Auto-discover recovery root from script location:
  sh /restore.sh --restore-folder /tmp/restored

  # Explicit:
  sh /restore.sh --restore-folder /tmp/restored /mnt/recovery

  # Skip Python tier:
  LCSAS_ALLOW_PYTHON_TIER=0 sh /restore.sh --restore-folder /tmp/restored /mnt/recovery

  # Non-interactive (password from env or file):
  LCSAS_PASSWORD='secret' sh /restore.sh --restore-folder /tmp/restored /mnt/recovery
  LCSAS_PASSWORD_FILE=/path/pw    sh /restore.sh --restore-folder /tmp/restored /mnt/recovery
