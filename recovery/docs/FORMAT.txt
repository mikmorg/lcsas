LCSAS RECOVERY TOOLCHAIN -- ON-DISC FORMAT
============================================

This document describes the on-disc data formats relevant to a restore.
It is derived from docs/RESTIC_FORMAT_SPEC.md and the LCSAS source.

REPOSITORY LAYOUT (restic format)

  repo/
    config                       encrypted; JSON; { "version": 1|2, "id": ... }
    keys/<keyid>                 each is an encrypted master-key file
    index/<indexid>              encrypted; JSON; { "packs": [...], "supersedes": [...] }
    snapshots/<snapid>           encrypted; JSON; { "tree": ..., "time": ..., "paths": [...] }
    data/<XX>/<packid>           pack files (two-level layout)
    data/<packid>                pack files (flat; LCSAS discs use two-level)

  Encrypted files use the AEAD format: IV(16) || ct || MAC(16).
  After decryption (and optional v2 prefix stripping), the result is
  raw JSON.

KEY FILE

  JSON object:
    {
      "hostname": "...",
      "username": "...",
      "kdf": "scrypt",
      "N":     32768,
      "r":     8,
      "p":     1,
      "salt":  "<base64>",
      "data":  "<base64>"
    }

  - The "salt" field is the scrypt salt (typically 32 random bytes).
  - The "data" field is the AEAD-encrypted master key (JSON form):
       { "encrypt": "<b64 32 bytes>",
         "mac": { "k": "<b64 16 bytes>", "r": "<b64 16 bytes>" } }
    encrypted under the key-encryption-key (KEK) derived from scrypt.

REPOSITORY V1 vs V2

  Versions 1 and 2 are a FROZEN, GATED contract (FMT-03): they are the
  only formats every recovery tier (this C reader, the pinned rustic
  fallback, and the tier-3 Python reader) can decode.  The burn
  pipeline decode-proves each mirror before mastering any volume and
  REFUSES to burn a repository whose live writer has migrated past
  v2 — so no disc that no shipped reader can open is ever produced.
  Bumping the set means changing all three readers together, not just
  upgrading the NAS rustic.

  Repository version 1: encrypted blobs decrypt directly to JSON / raw
  data.
  Repository version 2: a leading compression-type byte is prepended
  after decryption:
    0x00 -> uncompressed (strip the byte)
    0x01 -> zstd-compressed (strip; decompress remainder)
    0x02 -> zstd-compressed (strip; decompress remainder)

  For repository files (config, index, snapshots), the type byte is
  ALWAYS present in v2 (even when uncompressed: the byte is 0x00).

  For pack-blob inline data in v2 repositories, the leading byte is
  OMITTED if compressed: the zstd frame starts directly at the blob's
  offset.
  The implementation detects compression by checking the zstd magic
  number (28 B5 2F FD) at the start of decrypted data.

ZSTD MAGIC NUMBER

  Bytes:    28 b5 2f fd

PACK FILE FORMAT

  Layout (bytes, left-to-right, low-to-high offset):

    [ encrypted blob 0 ][ encrypted blob 1 ]...[ encrypted blob N-1 ]
    [ encrypted header ][ header_length (u32 LE) ]

  The trailing u32 LE specifies the length of the encrypted header.
  Subtract from file size to find header start.  The header is itself
  AEAD-encrypted; once decrypted, it is a packed binary structure:

    For each blob in the pack (37 bytes each):
      type        u8     (0=data, 1=tree, 2=padding)
      length      u32 LE
      id          32 bytes (SHA-256 of plaintext)

  The decrypted header is the sequence of these 37-byte entries.

  This is the format used by restic >= 0.10 ("packed format").

PACK FILE DISCOVERY

  Pack files are stored under data/, either:
    - Two-level: data/<XX>/<packid>  where XX is the first 2 hex chars
    - Flat:      data/<packid>

  Both layouts are supported.  Try two-level first.

LCSAS CATALOG

  Every data disc carries /catalog.db: a copy of the owner's SQLite
  catalog (the disc catalog), as it stood when the disc was staged.
  A restore does not need it.  Tier 1 and tier 3 use it to say which
  disc holds a pack; without it they ask for discs by pack instead.

  - Schema version: the "version" column of the one row in table
    schema_version (10 for discs from LCSAS 1.0).  Do NOT use
    PRAGMA user_version: LCSAS keeps the highest disc label number
    issued there, not the schema version.
  - Twelve tables: schema_version, repositories, packs, volumes,
    volume_packs, snapshots, locations, volume_copies, burn_sessions,
    session_volumes, volume_events, key_escrow.  The full schema is
    in the LCSAS source, db/schema.py: on the meta disc under
    lcsas/src/lcsas/, on a production data disc under lcsas_src/.
  - What a reader needs, and what later versions only add to:
      packs        (pack_id, sha256, size_bytes, repo_id)
      volume_packs (volume_id, pack_id)
      volumes      (volume_id, label, status)
    A pack's sha256 is its file name under data/.  Join packs to
    volume_packs to volumes to find the disc LABEL that holds it;
    skip volumes whose status is DESTROYED.  repo_id is the
    <repo_id> folder name under metadata/.
  - The disc's own row in volumes has status STAGING: the copy is
    taken before the disc is burned.  Discs staged in the same
    session may be missing from it.  The newest disc's catalog
    knows the most discs.
  - In the snapshots table the columns paths, tags and description
    are blank on a disc ("[]", "[]" and "" in every row; since
    v1.0.0-rc9, PR #771).  The owner's own catalog keeps them.  The
    real values are in each snapshot file under
    metadata/<repo_id>/snapshots/, encrypted with the repository's
    password (see SNAPSHOT FILE).
  - The file uses a rollback journal (journal_mode DELETE), not WAL,
    so it opens on a read-only disc.  Open it read-only (tier 1 uses
    the SQLite URI parameter immutable=1).

VOLUME LAYOUT (LCSAS data disc)

  Each data disc is an ISO 9660 image (with Rock Ridge and Joliet
  names) that dvdisaster has extended with RS03 error-correction
  data.  The ECC data sits in the image after the file system, not
  in a file.  The files on the disc:

  /data/<XX>/<packid>        pack files, two-level layout: <packid>
                             is the SHA-256 of the file, <XX> its
                             first two hex chars.  The packs of all
                             backup sets on the disc share this one
                             folder; the catalog's packs.repo_id says
                             which set each pack belongs to.
  /metadata/<repo_id>/       one folder for each backup set
                             (repository) of the archive, on every
                             data disc, also for a set with no packs
                             on this disc (if its files could be
                             read when the disc was staged).
                             <repo_id> is an id, not the set's name.
      config                 the repository's config file
      keys/                  its key files
      index/                 its index files
      snapshots/             its snapshot files: only those whose
                             packs are all on discs (this disc's
                             burn session counted)
      LCSAS_REPO.txt         backup set marker: plain "key=value"
                             lines (format, id, name, name_cmd,
                             split, split_id).  Restore works
                             without it.
  /catalog.db                the disc catalog (see LCSAS CATALOG)
  /standalone_restorer.py    the Python reader (tier 3)
  /volume_info.json          this disc: label, uuid, media type,
                             pack count, the repositories with packs
                             here, and the SHA-256 of every pack
  /START_HERE.txt, /RESTORE_INSTRUCTIONS.txt, /PASSWORD_INFO.txt,
  /VOLUME_INFO.txt, /CONFIG_SUMMARY.txt, /DISC_CARE.txt
                             notes for a person, in plain text
  /lcsas_src/                LCSAS Python source: restore/, utils/
                             and db/ (not on TEST_TINY test media)

  To read one backup set as a restic repository: take
  metadata/<repo_id>/ (config, keys/, index/, snapshots/) from any
  data disc (the newest disc knows the most snapshots) and the pack
  files of that set under data/ from every disc.

  How much fits: before packing a disc, LCSAS measures the catalog,
  the metadata folders, the reader, the text files and the ISO 9660
  overhead, and adds a tenth as a margin (since issue #811).  The
  packs fill the rest of the medium's capacity.

  The recovery tools (recovery/, with bin/<arch>/lcsas-restore,
  scripts/restore.sh and these docs), the bundled tools/ and the
  LCSAS source are on the separate meta disc (label LCSAS_META), not
  on data discs.  A meta disc built from the catalog also carries
  metadata/<repo_id>/ for each backup set, but no data/ and no
  catalog.db.

SNAPSHOT FILE

  JSON:
    {
      "time":     "2026-01-15T10:30:00.000Z",
      "tree":     "<64 hex chars>",
      "paths":    ["/home/alice"],
      "hostname": "machine.example.com",
      "username": "alice",
      "tags":     [...]
    }

TREE BLOB

  Plaintext JSON:
    {
      "nodes": [
        {
          "name":    "subdir-or-file-name",   /* must be a plain basename */
          "type":    "file" | "dir" | "symlink" | ...,
          "mode":    33188,
          "mtime":   "2026-01-15T10:30:00.123456789Z",
          "uid":     1000,
          "gid":     1000,

          /* For "file" */
          "size":    42,
          "content": ["<blob_id_hex>", "<blob_id_hex>", ...],
          "inode":   17654321,
          "links":   1,

          /* For "dir" */
          "subtree": "<blob_id_hex>",

          /* For "symlink" */
          "linktarget": "../somewhere",

          /* Optional */
          "extended_attributes": [{"name": "...", "value": "<base64>"}]
        },
        ...
      ]
    }

  Tree blobs are normal blobs (SHA-256 of plaintext = ID, present in
  the index, located in a pack file like any other blob).

NODE NAMES

  A node's "name" is stored as text.  When the real name holds a
  double quote, a backslash, a control character or a byte that is not
  valid UTF-8, rustic (and restic) store it in an escaped form, like a
  Go string without its outer quotes.  Decode it back to raw bytes
  before you create the file:

     \\  ->  \              \a  ->  byte 0x07
     \"  ->  "              \b  ->  byte 0x08
     \'  ->  '              \f  ->  byte 0x0c
     \`  ->  `              \n  ->  byte 0x0a
     \xHH       ->  the one byte 0xHH (two hex digits)
     \uHHHH     ->  that character, written as UTF-8
     \UHHHHHHHH ->  that character, written as UTF-8
     \r  ->  byte 0x0d      \t  ->  byte 0x09      \v  ->  byte 0x0b

  Every other character stands for itself (written as UTF-8).  Example:
  the stored text  latin\xe9.txt  is the 10-byte name "latin", byte
  0xE9, ".txt".  A name with no backslash is used as it is.  Only
  "name" is escaped this way: "linktarget" is plain text.

  Text that does not follow these rules (an unknown escape such as
  "\q", a backslash at the end, too few hex digits, a \u or \U value
  that is a surrogate or above 10FFFF) cannot be decoded.  Tiers 1 and
  3 then do not restore that node; they say so and end with an error.
  See lcsas_unescape_name in src/lcsas-restore/path.c.

PATH SAFETY

  When materializing a tree, check the DECODED name (see NODE NAMES):
   - REJECT a name that is empty, "." or "..", or that contains "/" or
     a NUL byte.
   - On Windows also REJECT a name that holds \ : * ? " < > | or a
     control character, or that is not valid UTF-8 (NTFS cannot store
     it).  On macOS REJECT a name that is not valid UTF-8.
   - A rejected name is never written under another name.  Tiers 1 and
     3 report each one ("NOT RESTORED"), restore everything else, and
     end with an error.
   - Symlinks whose "linktarget" is ABSOLUTE are restored as-is (matching
     rustic; see issue #187).  Containment of the restore tree is NOT
     guaranteed for absolute symlinks.  REJECT symlinks whose RELATIVE
     linktarget lexically escapes the restore root.

  See src/lcsas-restore/path.c.

CHECKSUMS

  Every blob is checked against its SHA-256 ID.  Every pack header is
  authenticated by Poly1305-AES.  Every encrypted file is authenticated
  by Poly1305-AES.  Tampering with any single byte produces an
  integrity failure that aborts the restore with a non-zero exit code.

  At the disc level, dvdisaster RS03 ECC provides additional integrity
  + repair beyond the cryptographic checks.

TIER-1 LIMITS

  Tier-1 JSON parsing (index files, snapshot files, tree blobs) is
  size-adaptive: the token buffer is grown on demand, so there is no
  fixed cap on the number of blob entries per index, directory entries
  per tree, or content blobs per file.  See lcsas_json_parse_alloc in
  src/lcsas-restore/json_q.c.

  The only ceilings are:
   - LCSAS_MAX_JSON_MIB (default 256) -- the maximum token-buffer memory
     in MiB for any single JSON structure.  A structure that needs more
     than this fails LOUD, naming the offending file and pointing at
     tier-2 (rustic); it is never silently skipped.  See ENV_VARS.txt.
   - a 256 MiB zstd decompression cap on any single repository file: if a
     decrypted file's zstd frame declares more than 256 MiB of content,
     tier-1 refuses to decompress it.  For an INDEX file this is now FATAL
     to load_index (T1C-05): it names the file, says "use tier-2 (rustic)",
     and aborts the load BEFORE any restore I/O -- rather than silently
     dropping the index and surfacing later as a cryptic "blob not in
     index".  A malformed (un-decodable) index frame is treated the same.
     Authentication (MAC) failure on a single stray index file stays
     non-fatal: it is warned, skipped, and counted in a summary line, so
     one corrupt file never sinks an otherwise-loadable repository.

  Both are escape hatches for memory-starved 32-bit hosts, not normal
  operating limits -- ordinary repositories never approach them.
